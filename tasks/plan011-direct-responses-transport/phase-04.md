# Phase 04 — 두 전송을 번갈아 측정한다

**Execution profile**: standard
**Status**: pending

---

## 목표

전송 교체의 효과를 잰다. **번갈아 재는 것이 이 phase 의 핵심이다.**

`plan010` 은 Phase 03(전송)과 Phase 05(스키마)를 **다른 시간대에** 각각 두 번 재서 비교했다.
그 방식은 호출 단위 변동은 막지만 **시간대 사이의 흐름은 막지 못한다** — 각 phase 의 두 회차가
같은 시간대를 공유하기 때문이다.

실제로 겪었다. 같은 A/B 를 한쪽을 먼저 몰아 돌렸을 때와 번갈아 돌렸을 때 **결론이 뒤집혔다.**

| 방식 | 결과 |
| --- | --- |
| A 를 먼저 8회, 그 다음 B 8회 | A 중위 9.9초·최대 44.0초, B 중위 7.9초 → "A 가 느리고 꼬리가 길다" |
| A·B 를 번갈아 8회 | A 중위 9.0초, B 중위 8.9초 → **차이 없음** |

**이 phase 는 Phase 03 이 머지된 상태를 전제한다.**

**범위 외**

- 코드 변경 — 측정만 한다. 결과가 나쁘더라도 여기서 고치지 않고 보고한다
- 의미 판정 — 하지 않는다. `plan006` 에서 36회 중 22회가 채점자 불일치로 `REVIEW` 였던 실측이 있어
  정보량이 낮다. 다만 **답변 길이는 반드시 집계한다** (아래 3번)
- 평가 세트 수정 — **한 글자도 건드리지 마라.** 비교선이 끊긴다
- `kg-eval` 러너 수정 — 교차는 실행 순서로 만든다. 스크립트를 고치지 않는다

## 작업 항목 (4)

### 1. 측정 전에 함정 파일을 읽는다

`docs/pitfalls/measurement.md` 를 읽는다. 여기서 반드시 지킬 셋이다.

- API 를 `pnpm` 으로 백그라운드에 띄우지 않는다
- 기동과 측정을 같은 명령에 묶지 않는다
- **측정 중 같은 API 로 다른 질의를 하지 않는다.** 이걸 어겨 결론이 뒤집힌 사건이 위 표다

### 2. 네 회차를 번갈아 돌린다

순서를 지킨다. **한 전송을 몰아 돌리지 마라.**

```
1회차: 직접 호출  →  2회차: 상주  →  3회차: 직접 호출  →  4회차: 상주
```

회차마다 전송 스위치를 바꾸고 API 를 다시 띄운다. 기동 로그에서 **전송 이름을 확인한 뒤** 측정한다.

```bash
# cwd: 저장소 루트
node .claude/skills/kg-eval/scripts/run.mjs \
  --suite eval/suites/tc-ocr-api-gateway.json \
  --stage plan011-direct-1 \
  --api-base-url http://localhost:3000 \
  --query-model gpt-5.6-terra \
  --out eval/runs/plan011-direct-1.json
```

`--stage` 에 전송과 회차를 담아 나중에 어느 파일이 무엇인지 헷갈리지 않게 한다.

`--query-model` 은 선언값일 뿐이고 런타임 모델을 증명하지 않는다. 리포트에 그렇게 적는다.

### 3. 지연·회수·답변 길이를 각각 집계한다

**`compare.mjs` 를 쓰지 마라.** `run.mjs` 출력 형식과 맞지 않고 종료 코드 0 으로 조용히 실패한다
(`docs/retrospectives/0015-compare-script-fails-with-exit-zero.md`).

출력 파일에서 직접 집계한다. 필드 경로는 확인된 것이다.

| 지표 | 경로 |
| --- | --- |
| 지연 | `attempts[].latencyMs` |
| 실패 경계 | `attempts[].deterministicChecks.failureBoundary` |
| 답변 길이 | `attempts[].answer` 의 길이 |
| 세트 동일성 | 최상위 `suiteHash` |

**답변 길이를 꼭 집계하는 이유** — 직접 호출은 에이전트 시스템 프롬프트가 빠져 문체가 바뀐다.
실측에서 같은 프롬프트에 554자 대 712자였다. 지연만 보면 이 변화가 안 보인다.

한글 길이를 잴 때 escape 여부를 구분한다. 파이썬 `json.dumps` 는 기본이 `\uXXXX` 라
같은 문자열이 다른 길이로 보인다 — 실측으로 34,615자와 57,466자로 갈린 사건이 있다.

### 4. 구간으로 판정한다

| 구간 | 회차 |
| --- | --- |
| 직접 호출 | 1·3회차 |
| 상주 (동시대 기준값) | 2·4회차 |

**구간이 겹치면 개선이라 부르지 않는다.** 겹친다고 적는다.

`plan010` 최종 수치(54.1\~59.5초)와도 대조하되, **그건 다른 시간대의 값이라 참고로만 쓴다.**
이 phase 의 상주 회차가 동시대 기준값이다.

## 검증

- 네 회차의 `suiteHash` 가 모두 같다
- 회차마다 기동 로그의 전송 이름을 확인했고 그 기록을 결과에 남겼다
- 각 회차의 attempt 수와 오류 건수를 적었다
- 실제로 측정한 문항 수를 적었다 — 부분 재측정으로 전체를 단정한 사건이 있었다

측정 후 띄운 프로세스를 정리하고, 무엇을 남기고 무엇을 지웠는지 결과에 적는다.
`Codex.app` 이 소유한 `app-server` 프로세스는 건드리지 마라.

## 의도 메모 (왜)

- **번갈아 재는 이유** — 위 표가 근거다. 같은 코드로 몰아 재면 반대 결론이 나왔다.
  이건 이 저장소에서 실제로 겪은 일이고, 지금까지의 지연 판정이 이 구멍을 갖고 있었다
- **네 회차인 이유** — 전송당 두 회차가 있어야 구간이 생긴다. 한 회차씩이면 구간이 없다
- **답변 길이를 함께 재는 이유** — 이 변경은 순수한 전송 교체가 아니다. 시스템 프롬프트가 빠져
  문체가 바뀐다. 그 변화를 안 재면 "지연이 줄었다" 는 결론이 반쪽이다
