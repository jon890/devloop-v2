# ADR 0004 — 정규화를 순수 함수로 떼고 그 산출물은 조사 전용으로 둔다

- 상태: 채택
- 결정일: 2026-07-29
- 기록일: 2026-07-29

## 맥락

`sync-neo4j` 가 875줄이고 안에 성격이 다른 관심사가 섞여 있었다.

| 관심사 | 규모 | 문제 |
| --- | --- | --- |
| 정규화 (별칭 치환·엔드포인트 해석·노드 병합) | 약 340줄 | Neo4j 의존이 0인데 적재 파일에 있다 |
| Neo4j 쓰기 | 약 160줄 | — |
| 일회성 마이그레이션 | 약 20줄 | 매 적재마다 조건 없이 실행된다 |
| 입력 읽기·통계·오케스트레이션 | 나머지 | — |

실무에서 걸린 문제는 이것이다. **별칭 사전을 고쳤을 때 무엇이 합쳐지는지 적재 없이 볼 수 없다.**
정규화가 적재에 묶여 있고, 적재기가 MERGE 전용이라 틀리면 그래프를 초기화해야 한다.

경계를 흐리는 것이 둘 더 있었다.

- **적재가 추출 산출물을 덮어쓴다** — 적재 중 관계 정리기가 `inferred.jsonl` 을 `writeFile` 한다
- **사전 로딩이 두 곳에 각자 구현돼 있다** — 추출과 적재가 같은 사전을 다르게 읽을 수 있다

## 검토한 안

| 안 | 방식 | 판단 |
| --- | --- | --- |
| `--dry-run` 플래그 | `sync-neo4j` 에 플래그를 붙여 정규화 결과만 출력한다 | 단계·파일이 늘지 않는다. 다만 비교하려면 매번 두 번 실행해 출력을 받아야 하고, 정규화만 재실행하는 경계가 생기지 않는다 |
| `resolved.jsonl` 을 **파이프라인 입력**으로 | `resolve-graph` 가 파일을 쓰고 `sync-neo4j` 가 그 파일을 읽는다 | 진짜 단계 체인이 된다. 다만 **stale 위험**이 생긴다 — 앞 단계를 고치고 `resolve` 를 안 돌리면 옛 결과로 적재된다 |
| **`resolved.jsonl` 을 조사 전용으로** | `resolve-graph` 가 파일을 쓰고, `sync-neo4j` 는 같은 순수 함수를 직접 부른다 | 채택 |

## 결정

**정규화를 순수 함수로 `resolve/` 에 떼어낸다. 두 명령이 그 함수를 공유한다.**

```
resolve-graph:  읽기 → 정리 → 정규화 → 파일 쓰기 (resolved.jsonl · resolve-report.json)
sync-neo4j:     읽기 → 정리 → 정규화 → Neo4j 쓰기
```

`sync-neo4j` 는 **`resolved.jsonl` 을 읽지 않는다.** 매번 새로 정규화한다.
`resolved.jsonl` 은 파이프라인 입력이 아니라 **사람이 들여다보는 산출물**이다.

## 이유

이 저장소의 단계 경계 기준이 결정을 갈랐다.

> 재실행 비용이 다르면 단계를 나눈다.

**정규화는 공짜다.** 결과를 파일에 캐싱해 적재에 먹여도 **아끼는 것이 없다.**
얻는 것은 없고 stale 위험만 새로 생긴다. 이 저장소는 이미 같은 계열의 함정을 여러 번 겪었다 —
Vite 사전 번들 캐시, 테스트 glob, 문서의 옛 참조. 캐시가 조용히 낡는 구조를 또 들일 이유가 없다.

파일의 값어치는 전부 **들여다보기**에 있다. 그러면 파이프라인 입력으로 만들 필요가 없다.

## 결과

**좋은 쪽**

- 별칭 사전을 고친 전후를 `cmp` 한 번으로 비교한다. 적재도 초기화도 필요 없다

  ```bash
  pnpm --filter pipeline resolve-graph --out /tmp/before.jsonl
  # 사전 수정
  pnpm --filter pipeline resolve-graph --out /tmp/after.jsonl
  cmp /tmp/before.jsonl /tmp/after.jsonl
  ```

- **적재가 추출 산출물을 덮어쓰는 문제가 함께 사라진다.** 정리가 순수 함수로 메모리에서 돌고
  파일 출력은 `resolve-graph` 단독 실행 때만 일어난다
- 정규화가 Neo4j 없이 테스트된다
- 사전 로딩이 한 곳으로 모인다

**대가**

- **같은 순수 함수를 두 명령이 부른다.** 호출처가 둘이라 한쪽만 고치면 어긋날 수 있다.
  함수가 하나이므로 구현 중복은 없지만, 인자 조립이 갈릴 여지가 있다
- `resolved.jsonl` 이 파이프라인 입력이 아니라는 것을 **문서로만 알 수 있다.** 파일 이름만 보면
  다음 단계 입력처럼 보인다. `docs/flow.md` 의 다이어그램에서 체인 옆에 붙여 표시한다
- 산출물이 둘 늘어난다 (`resolved.jsonl`·`resolve-report.json`)

### 재현성이 전제다

dry-run 비교가 성립하려면 **같은 입력이 같은 바이트를 내야 한다.**
출력 순서를 고정한다 — 노드는 `라벨 → 키 → tie-break`, 관계는 `유형 → 시작키 → 끝키 → tie-break` 다.
tie-break 는 그 레코드를 파일에 쓸 때 실제로 쓰는 `JSON.stringify` 직렬화 결과 자체다 — 앞선 키가
모두 같은 동순위 레코드(예: 식별 속성만 다른 관계)에서도 이 값으로 전순서가 서고, 정렬 비교와
출력 바이트가 같은 값이라 "비교에서 동순위면 바이트도 같다" 가 구성상 보장된다.
정렬은 기존 `compareCodePoints` 를 재사용한다.

이 성질이 깨지면 `resolved.jsonl` 의 존재 이유가 없어진다. 그래서 **두 번 실행해 `cmp` 로
바이트 동등을 확인하는 것**을 구현 통과 조건에 넣는다.

## 함께 정리한 것

**죽은 마이그레이션 두 개를 지운다.** 매 적재마다 조건 없이 실행되고 있었다.

| 함수 | 목적 | 실측 |
| --- | --- | --- |
| `migrateTaskNumberType` | `Task.number` 를 정수로 강제 | 적재기가 이미 정수를 쓴다. 490건 전부 `INTEGER NOT NULL` |
| `removeLegacyUnknownTagDimensions` | `TAGGED{dimension:'unknown'}` 삭제 | `dimension` 이 `0`·`1`·`2` 뿐. `unknown` 0건 |

옛 코드로 적재된 그래프를 고치려던 것이고, 현재 적재기는 그 상태를 만들지 않는다.
옛 그래프를 만나면 초기화 후 재적재로 다룬다 — `jsonl` 이 남아 있어 항상 가능하다.

그 자리에 **`reset-neo4j`** 를 만든다. 지금까지 손으로 하던 `DETACH DELETE` 절차에 이름을 준다.

- `NEO4J_URI` 가 없으면 실행하지 않는다 (기본값을 두지 않는다) — 근거는 `docs/data-schema.md` 대상 명시 규칙
- `--force` 없이는 실행하지 않는다
- 대상 포트가 운영(`7687`)이면 `--allow-production` 도 함께 줘야 한다
- 대상 URI 와 현재 노드 수를 먼저 출력한다
- 삭제 범위는 **전체**다. 프로젝트 단위 삭제는 만들지 않는다 —
  `Task.number` 가 프로젝트를 구분하지 않아 부분 삭제가 안전하지 않다
