# ADR 0001 — 온톨로지를 고정 스키마로 둔다

- 상태: 채택
- 결정일: 2026-07-22 (깊이 인터뷰 R8)
- 기록일: 2026-07-29

## 맥락

LLM 이 업무·위키 본문에서 개체와 관계를 추출한다. 그 개체·관계의 종류를 누가 정하는가가 문제였다.

원래 가정은 "온톨로지는 agent 가 알아서 만든다" 였다. 인터뷰 R8 에서 세 안을 비교했다.

## 검토한 안

| 안 | 방식 | 문제 |
| --- | --- | --- |
| 자동 생성 | LLM 이 본문을 보고 스키마를 만든다 | 실행마다 라벨·관계가 달라져 재현이 안 된다. 질의 Cypher 를 쓸 수 없다 |
| 자동 진화 | 고정 스키마로 시작해 LLM 이 필요할 때 확장한다 | 확장 시점의 판단을 검증할 수단이 없다. 언제 무엇이 늘었는지 추적이 어렵다 |
| **고정 스키마** | 사람이 정한 라벨·관계만 허용한다 | 새 개체 유형이 필요하면 사람이 계약을 고쳐야 한다 |

## 결정

**고정 스키마로 간다.** 자동 진화는 이후 과제로 남긴다.

LLM 은 이 틀 안에서 추출만 한다. 허용된 라벨·관계 밖의 것을 만들면 적재 단계에서 버리고 리포트에 집계한다.

이 결정의 적용 범위는 Neo4j GraphRAG 경로다.
[ADR 0010](0010-experience-memory-parallel-lane.md)의 Experience Memory 파일 경로는 graph ontology를 사용하지 않는다.

## 이유

- **질의가 Cypher 를 생성한다.** 스키마가 실행마다 바뀌면 질의 프롬프트에 넣을 계약이 없다
- **품질 측정이 성립한다.** 같은 스키마라야 회귀를 판정할 수 있다
- 도메인 모델이 인터뷰에서 **4라운드 연속 무변동으로 수렴**했다. 자동 생성이 필요할 만큼 유동적이지 않았다

## 결과

**좋은 쪽**

- 질의 프롬프트에 온톨로지 계약을 그대로 넣을 수 있다
- 스키마에 없는 관계를 버리는 검증 지점이 생겼다. 실제로 LLM 이 만든 잘못된 관계를 걸러 낸다
- 노드·관계 통계로 적재 결과를 검증할 수 있다

**대가**

- 새 개체 유형이 필요하면 계약을 고쳐야 한다. 저장소 코드 지식을 통합하려면 `Repository`·`Deployment` 를 계약에 더해야 한다
- **관계를 추가할 때 질의 쪽이 그 관계를 아는지 따로 확인해야 한다.** 온톨로지에 정의만 하고
  질의 프롬프트에 알리지 않으면 조용히 도달 불가가 된다. `DOCUMENTS` 에서 실제로 겪었다

## 관련

- `docs/data-schema.md` — 확정된 라벨·관계
- `packages/shared/src/ontology/` — 실행 소스
