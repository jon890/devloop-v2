# ADR 0008 — LLM 을 상주 app-server 로 호출한다

- 상태: 채택
- 결정일: 2026-08-04
- 기록일: 2026-08-04

## 맥락

질의 1건이 44~59초 걸린다. 질의당 LLM 호출은 3~5회다 (`docs/flow.md`).

호출 하나를 분해하면 **모델이 답하는 시간보다 프로세스를 띄우는 시간이 크다.**

| 구간 | 시간 |
| --- | --- |
| `codex` 프로세스 기동 | 약 8초 |
| 모델 응답 | 약 4초 |

`codex exec` 는 호출마다 프로세스를 새로 띄운다. 3~5회면 **기동만으로 24~40초**다.

평가도 같은 값을 낸다. 12문항 3회 측정이 36회 순차 실행이라 한 번 재는 데 약 35분이 든다.
반복 측정이 품질 판정의 전제인데(ADR 0002) 그 반복이 느리다.

## 결정

**LLM 호출을 상주 `codex app-server` 로 보낸다.**

- 전송은 WebSocket JSON-RPC 다. `initialize` → `thread/start` → `turn/start` 순서로 부른다
- **호출마다 새 thread 를 쓴다.** 같은 thread 는 앞 턴의 대화를 다음 턴에 남긴다
- **서버는 각 프로세스가 자기 것을 자식으로 띄우고 종료할 때 죽인다.** 포트는 `0` 으로 맡기고
  서버가 stdout 에 출력하는 포트를 읽는다
- API 응답 계약은 `turn/start` 의 `outputSchema` 로 서버에 넘긴다
- `codex exec` 어댑터는 제거한다. `claude -p` 어댑터는 남긴다
- 클라이언트는 `packages/llm` 이 소유하고 API 와 파이프라인이 함께 쓴다

**ADR 0002 를 대체하지 않는다.** 같은 구독 계정이고 `codex` CLI 의 공식 실행 모드다.
종량제 API 로 바꾸는 것이 아니므로 "구독 CLI 만 쓴다" 는 제약은 그대로 유효하다.

## 이유

실측이다. 27KB 프롬프트로 세 번씩 재고 평균을 냈다.

| 호출 방식 | 최소 프롬프트 | 27KB 프롬프트 |
| --- | --- | --- |
| `codex exec` | 8.0~12.0초 | 11.3~14.4초 |
| 상주 모드 | 2.0~5.5초 (평균 3.5) | 3.9~8.5초 (평균 5.6) |

`initialize` 는 0.00초, `thread/start` 는 0.14초다. **기동 8초가 사라진다.**

`outputSchema` 도 실측했다. 프롬프트에 형식 지시를 한 글자도 넣지 않고 비교했다.

| | 응답 | 계약 준수 |
| --- | --- | --- |
| `outputSchema` 있음 | `{"terms":[...]}` | 예 |
| `outputSchema` 없음 | 산문 | 아니오 |

**스키마는 모양만 보장하고 내용은 보지 않는다.** 모델이 `terms` 배열 안에 설명을 섞어 넣었다.
그래서 프롬프트에서 빼는 것은 형식 지시 문구뿐이고 내용 지시는 남긴다.

## 기각한 대안

| 대안 | 기각 사유 |
| --- | --- |
| `codex exec-server --listen ws://` | 미구현이다. `thread/start` 가 `exec-server stub does not implement` 를 반환한다 |
| `app-server daemon` 제어 소켓에 직접 붙기 | JSON-RPC·LSP 두 프레이밍 모두 무응답이었다 |
| 고정 포트 하나를 두 앱이 공유 | 누가 죽이는지가 모호하고, 떠 있는 서버가 이상해졌을 때 붙는 쪽이 원인을 모른다 |
| 호출마다 같은 thread 재사용 | 앞 턴이 다음 프롬프트에 남는다. 지연만 고치려던 변경이 답변 내용까지 바꾼다 |
| 더 빠른 모델로 교체 | 상주 모드에서 `gpt-5.6-luna` 7.2초 대 `gpt-5.6-terra` 5.6초로 차이가 표본 안에 묻힌다.<br>지연의 원인은 모델이 아니라 프로세스 기동이었다 |
| 파이프라인 추출에도 `outputSchema` 적용 | 추출 스키마가 `@devloop/shared` 의 zod 3 스키마를 참조해 계약 패키지까지 zod v4 로<br>올려야 하고, `superRefine` 의 교차 필드 규칙은 JSON Schema 로 표현할 수 없어 재시도가 남는다.<br>추출 프롬프트를 바꾸면 캐시 537건이 무효화돼 그래프까지 다시 적재해야 한다 |

## 결과

**좋은 쪽**

- 질의 지연이 내려간다. 호출당 12초에서 5초 수준이다
- 측정 반복이 빨라진다. 한 번 재는 데 약 35분에서 약 15분이다
- API 의 JSON 계약 재시도가 사라진다. 형식 위반으로 호출이 두 배가 되는 경로가 없어진다

**대가**

- **서버 하나에 질의 전부가 매달린다.** 죽으면 모든 호출이 실패한다.
  `codex exec` 는 호출마다 독립이라 이 결합이 없었다
- 프로세스 생명주기 코드가 늘어난다. 띄우고, 준비를 확인하고, 죽인다
- 실패가 JSON-RPC 오류가 아니라 `turn/completed` 의 `turn.status` 로 온다.
  이걸 안 보면 실패를 성공으로 읽는다
- 원인을 볼 곳이 하나 늘어난다. 서버 stdout 로그를 함께 봐야 한다

## 관련

- ADR 0002 — 구독 CLI 제약. 이 결정이 그 제약 안에 있다
- ADR 0003 — 모델 지정 누락 사고. `turn/start` 도 모델을 인자로 받으므로 같은 함정이 있다
- `docs/flow.md` — 질의당 호출 지점과 서버 생명주기
