# 0005 — 사람이 내린 Concept 판단을 관계형 저장소에 둔다

**상태**: 채택

## 결정

어떤 Concept 표기가 같은 개체인지에 대한 사람의 판단을 관계형 저장소에 두고,
원천에서 자동 생성되는 표준 사전과 분리한다.
판단은 프로젝트 단위로 귀속시키고, 소스가 늘어도 소스 단위로 쪼개지 않는다.

## 맥락

표기 정규화로 잡히지 않는 파편화는 자동으로 병합할 수 없다.
부분포함 후보가 천 쌍 넘게 탐지되지만 대부분 오탐이고,
토큰 집합이 완전히 같은데 다른 개체인 사례도 실측으로 나왔다.
그래서 판단은 사람이 근거를 보고 내려야 하는 자산이 된다.

그런데 그 판단이 세 곳에 흩어져 있었다.
별칭은 자동 생성되는 사전 파일에 섞여 있었고, 차단 목록과 canonical 지정은 전역 상수였다.
성질이 같은 판단인데 저장 위치와 적용 범위가 달랐다.

더 나쁜 것은 생성이 판단을 지운다는 점이다.
사전 생성 단계가 원천 제목에서 이름을 다시 뽑아 표준어로 만들고,
별칭이 다른 항목의 표준어와 겹치면 그 별칭을 버린다.
두 규칙이 맞물려 사람이 등록한 별칭이 조용히 사라진다 — 실측으로 확인했다.

전역 상수는 저장소에 커밋되므로 조직 내부 이름이 코드 이력에 남는 문제도 함께 있었다.

## 기각한 대안

**파일에 두고 생성 단계가 보존하게 만든다.**
생성 규칙과 사람 판단이 같은 파일에서 다투는 구조가 그대로 남는다.
무엇보다 모순을 넣는 시점에 막을 수 없다 —
한 표기가 서로 다른 두 표준어에 동시에 귀속되면 지금은 **적재 도중 예외로** 드러난다.
잘못을 입력에서 잡지 못하고 파이프라인 실행에서 잡는 구조다.

**지식그래프에 함께 둔다.**
이 저장소의 표준 초기화 절차가 그래프 전체 삭제다.
판단을 그래프에 두면 초기화가 사람 판단까지 지운다.
데이터를 되살리는 절차가 판단을 파괴하는 구조는 받아들일 수 없다.

**파일 기반 임베디드 저장소로 제약만 얻는다.**
제약과 트랜잭션은 얻지만, 승인 화면과 API 가 붙는 순간 서버형 저장소가 필요해진다.
화면을 만들기로 정했으므로 나중에 두 번 옮기지 않고 지금 정한다.

## 결과

한 표기가 최대 하나의 판단에만 지배된다는 불변식을 유일성 제약으로 강제한다.
적재 도중 터지던 충돌이 등록 거부로 바뀐다.
그 결과 키 충돌을 사람이 풀어 주기 위해 두었던 canonical 지정 표는 존재 이유가 사라져 없앤다.

표준 사전을 읽는 단계는 저장소를 요구한다.
접속 정보가 없거나 접속에 실패하면 즉시 실패한다 — 판단을 조용히 빼고 진행하면 잘못된 그래프가 만들어진다.
[0003](0003-fail-fast-config.md) 과 같은 원칙이다.
반면 사전을 쓰지 않는 수집·구조 파싱 단계는 저장소를 건드리지 않아 오프라인 성질을 유지한다.

판단은 커밋되지 않으므로 잃을 수 있다.
그래서 내보내기 명령으로 덤프를 만들어 저장소 밖에 보관하는 것을 절차에 포함한다.
덤프는 같은 상태면 같은 바이트가 나오게 만들어 비교로 변경을 읽을 수 있게 한다.

정규화 자체는 순수 함수로 남고 조회는 입출력 경계에 머문다.
[0004](0004-resolve-as-inspection-stage.md) 의 구조는 유지된다.
