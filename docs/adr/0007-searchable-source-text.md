# ADR 0007 — 원천 텍스트를 검색 가능한 분량으로 보존한다

- 상태: 채택
- 결정일: 2026-08-03
- 기록일: 2026-08-03

## 맥락

plan005 기준선에서 실패 경계가 `RETRIEVAL` 19 · `ANSWER` 2 · `GRAPH` 0 으로 나왔다.
그래프 정합은 깨끗한데 필요한 근거를 못 물어오는 단계에서 절반이 멈춘다.

실패 문항을 살아 있는 API 로 직접 던져 원인을 갈랐더니 성격이 서로 달랐다.

| 관측 | 원인 |
| --- | --- |
| 질문의 단어가 정답 댓글에 그대로 있는데 못 찾는다 | 댓글이 검색 대상이 아니다 |
| 필요한 업무를 다 물어왔는데 판정은 실패다 | gold 가 구조로 증명된 것을 댓글로 요구했다 |
| Cypher 가 7개 업무를 정확히 지정했는데 하나가 빠졌다 | 실행 행 상한이 노드를 통째로 떨어뜨렸다 |

첫 번째를 파고들다 더 깊은 문제를 찾았다. **그래프에는 원천 텍스트의 머리 부분만 들어 있다.**
업무 본문은 300자, 댓글은 200자에서 잘린다. 원천 중앙값이 각각 414자와 495자이므로
댓글의 79%가 잘린 상태다. 평가 세트가 필수 근거로 지목한 댓글 14건은 예외 없이 잘린다.

한 사례가 문제를 압축해 보여 준다. 어떤 질문은 병목과 조치를 함께 묻는데,
정답 댓글에서 병목은 앞 200자에 있고 조치는 그 뒤에 있다.
검색이 그 댓글을 찾아냈더라도 조치 내용이 그래프에 없어 답할 수 없다.
즉 회수만의 문제가 아니라 **애초에 담기지 않은 것**이 있었다.

## 결정

**원천 텍스트를 검색과 인용이 가능한 분량으로 보존하고, 그 텍스트를 전문 검색 대상에 넣는다.**

- 업무 본문과 댓글의 저장 상한을 6,000자로 둔다
- GitHub 훅 댓글은 버리지 않고, 훅 형식으로 판정된 것에 한해 머리말만 벗긴다
- 검색이 댓글을 찾으면 앵커 목록에 넣지 않고 부모 업무로 승격한다

## 이유

**상한 6,000자** — 평가 세트의 필수 근거 댓글을 전부 담는 최소값이다.
2,000자면 14건 중 10건, 5,000자면 13건이고 6,000자에서 전부 덮인다.
값을 크게 잡을수록 답변 합성 프롬프트가 커지므로, 근거가 아니라 여유로 올리지 않는다.

**훅 머리말만 벗긴다** — 훅 댓글 359건은 예외 없이 커밋 메시지를 달고 있고,
평가 세트가 필수 근거로 지목한 것도 그중 2건이다.
버리면 변경값과 배포 기록이라는 가장 신뢰도 높은 근거가 사라지고,
보류해 둔 저장소 통합이 원하던 것을 미리 버리는 셈이 된다.
잡음의 실체는 댓글이 아니라 매번 같은 모양으로 반복되는 링크 머리말이며 그 분량이 전체의 60%다.

**벗기기 규칙은 훅 판정에 묶는다** — 처음에는 "앞쪽 링크 줄을 걷어낸다" 는 넓은 규칙을 생각했다.
실측하니 사람이 멘션이나 불릿으로 시작한 댓글 317건이 함께 깎였고 한 건은 304자가 사라졌다.
훅 머리말은 두 줄 고정 형태이므로 그 모양일 때만 벗기도록 좁혔고,
좁힌 규칙은 훅 359건을 전부 잡으면서 사람 댓글은 한 건도 건드리지 않는다.
판정과 제거를 전용 모듈이 소유하게 해서, 훅 종류가 늘어날 때 그 모듈만 보면 되게 한다.

**댓글을 부모 업무로 승격한다** — 앵커는 LLM 에게 "이런 노드가 실제로 있다" 고 알려 주는 출발점이다.
댓글을 그대로 넣으면 Cypher 생성 프롬프트가 새 라벨을 다루는 법을 알아야 하고,
같은 업무의 댓글 여러 건이 앵커 슬롯을 잠식한다.
부모로 승격하면 앵커 라벨 구성이 그대로여서 프롬프트를 건드리지 않고,
같은 업무의 댓글이 하나로 합쳐져 슬롯 경쟁도 덜하다.
무엇보다 변경 범위가 좁아 **회수 실패가 줄었을 때 텍스트 확보 덕이라고 말할 수 있다.**

## 기각한 대안

**GitHub 훅 댓글을 수집하지 않는다** — 처음 검토한 방향이다.
댓글이 소통 성격이라 잡음이라는 판단이었는데, 실측이 반박했다.
순수 머리말만 있는 훅 댓글은 0건이고 359건 전부 커밋 메시지를 담는다.
제외하면 특정 문항이 영구히 답할 수 없는 상태가 된다.

**지금 있는 발췌에 인덱스만 건다** — 가장 싸다.
그러나 필수 근거 댓글 14건이 모두 잘린 상태라 검색이 닿는 범위가 머리 부분에 갇히고,
찾아낸 뒤에도 인용할 내용이 없다.

**검색용 속성과 표시용 발췌를 분리한다** — 인덱스에는 전문을 넣고 프롬프트에는 매칭 구간만 넣는 방식이다.
정확하지만 온톨로지 속성이 늘고 구간 추출 로직이 새로 필요하다.
상한 상향으로 필수 근거가 전부 덮이므로 지금은 값이 비용을 넘지 않는다.
상한으로 안 덮이는 문항이 실측으로 남으면 그때 근거를 갖고 다시 본다.

**벡터 유사도 검색을 먼저 넣는다** — 방향으로는 맞고 순위 융합 구조가 이미 갖춰져 있다.
그러나 임베딩할 텍스트가 200자뿐인 상태에서 벡터를 얹으면 어휘 검색과 같은 맹점을 물려받는다.
텍스트 확보가 벡터의 선행 조건이다.
임베딩 제공자 문제도 남아 있다 — ADR 0002 가 종량제 API 를 금지하는데 구독 CLI 는 임베딩을 주지 않는다.

## 결과

**좋은 쪽**

- 되돌릴 수 없는 작업이 없다. 적재기가 속성을 덮어쓰므로 초기화 없이 재적재만으로 반영된다
- 새 의존이 없다. 기존 `cjk` analyzer 가 한국어를 두 글자씩 겹쳐 쪼개 띄어쓰기 차이를 흡수한다
- 온톨로지 속성이 늘지 않아 ADR 0001 의 고정 스키마 계약을 건드리지 않는다

**대가**

- 근거가 길어져 답변 합성 프롬프트가 커진다. 재측정 때 질의 소요 시간을 함께 기록해 비용을 드러낸다
- 검색 대상이 늘어 `/api/graph/search` 결과에 댓글이 섞인다. 목록 표시 문자열을 짧게 잘라 대응한다
- 상한을 넘는 텍스트는 여전히 잘린다. 조용한 손실이 되지 않게 `parse-structure` 가 잘린 건수를 출력한다

## 관련

- ADR 0001 — 고정 온톨로지 스키마
- ADR 0002 — 구독 CLI 제약. 벡터 도입을 막고 있는 조건이다
- ADR 0006 — 원천 근거 기반 평가. 이 결정의 판정 근거를 제공한다
