# 지식그래프 품질 rubric — 온톨로지 기준·질문 역설계·채점표

품질 통과 조건의 단일 소스다.
평가 스킬(`kg-eval-human`, `kg-eval-ai`)이 이 문서의 채점표와 통과선을 따르고,
stage commit 마다 실행해 축별 통과 조건을 모두 충족할 때까지 개선 루프를 돈다.

## 1. 온톨로지 정적 기준 (그래프 자체의 높은 기준)

질의와 무관하게 적재된 그래프가 항상 충족해야 하는 기준.
Cypher 한 줄로 측정 가능해야 하며, 파일럿 단계부터 매 평가에 포함한다.

| #   | 기준               | 측정                                                            | 통과선 |
| --- | ------------------ | --------------------------------------------------------------- | ------ |
| S1  | 스키마 정합        | 온톨로지 계약 밖 라벨·관계 수                                   | 0      |
| S2a | 정규화 회귀        | 적재기 정규화 후에도 표기만 다른 채 남은 Concept 노드 비율      | < 1%   |
| S2b | 근사 중복 탐지     | 어순 차이·부분포함으로 중복 의심인 Concept 쌍 수                | 측정·기록 |
| S3  | 사전 적중          | 연결 수 5개 이상 고빈도 Concept 중 사전(canonical+alias) 매칭 비율 | ≥ 50%  |
| S4  | 연결성             | 고아 Task(CONTAINS 외 관계 0) 비율                              | < 10%  |
| S5  | 추출 밀도          | Task 당 평균 MENTIONS 관계 수                                   | ≥ 1.5  |
| S6  | 근거 추적          | LLM 생성 노드·관계 중 출처 문서 id(sourceDocId) 보유 비율       | 100%   |
| S7  | 질문 의도 커버리지 | 아래 6개 의도 유형별로 답을 표현할 스키마 경로 존재             | 6/6    |

의도 유형 (S7): 원인·히스토리 / 담당·사람 / 문서·참고 / 의존·구조 / 상태·진행 / 집계·통계.

### S2 를 두 축으로 나눈 이유

이전 S2 는 "부분포함 근사 중복" 으로 셌는데 오탐이 대부분이었다 — `Document` 가 `Document.Console` 에 포함되지만 둘은 별개 개체다 (실측 694쌍 중 진짜 파편화는 35그룹).

그 반대로 "표기 정규화 후 동일" 로만 재면 **적재기의 정규화 함수와 판정식이 같아져 통과가 구조적으로 보장된다** — 정적 기준이 감시 기능을 잃는다.

그래서 목적을 나눈다.

- **S2a (정규화 회귀)**: 적재기 정규화가 깨졌는지 감시한다. 정상 상태에서는 통과가 보장되는 것이 맞다 — denylist 로 의도적으로 남긴 노드만 남기 때문이다. 이 값이 오르면 적재기 회귀 신호다
- **S2b (근사 중복 탐지)**: 적재기가 아직 잡지 못하는 새 유형(어순 차이·부분포함)을 발견한다. 오탐이 섞이므로 통과선을 걸지 않고 측정·기록만 하며, 사람이 훑어 사전 별칭 보강 대상을 고른다

### S3 통과선을 50% 로 정한 근거

이전 기준 80% 는 달성 불가능했다. 사전은 태그·위키 제목에서 시드되는데 LLM 은 본문 전체에서 개념을 뽑으므로, 코드 심볼 같은 정당한 신규 개념이 항상 사전 밖에 있다 (전체 기준 실측 11.7%).

대상을 고빈도 Concept(연결 5개 이상)으로 좁힌 실측이 46.36% 다.
고빈도 개념은 사전에 있어야 한다는 취지이므로 50% 를 통과선으로 두되, **현재는 미달 상태**임을 인정한다.
사전 별칭 보강으로 올려야 하는 목표치이고, 이 수치가 오르면 앵커 도달률도 함께 개선된다.

## 2. 질문 방식 역설계

### 사람은 이렇게 묻는다 (kg-eval-human 질문 은행의 생성 규칙)

| 패턴                    | 특징                                                   | 예 (tc-ocr)                           |
| ----------------------- | ------------------------------------------------------ | ------------------------------------- |
| H1 모호한 지칭          | 대상을 이름 대신 사건·맥락으로 지칭                    | "게이트웨이 뗀 거 왜 그랬지?"         |
| H2 별칭·부분 이름       | 공식 명칭 대신 줄임말·구어                             | "모델서버 죽었을 때 볼 문서 뭐 있지?" |
| H3 상대 시간            | 절대 날짜 없이 최근·작년·저번                          | "최근에 부하테스트 관련해서 뭐 했지?" |
| H4 행동 지향            | 답을 받아 다음 행동(코드 위치·담당자·문서)으로 가려 함 | "쿠콘 장애 나면 어디 코드 봐야 해?"   |
| H5 짧은 질문, 깊은 기대 | 질문은 한 줄이지만 답은 multi-hop 이어야 함            | "GPU 부족해서 했던 작업들 뭐야?"      |

### AI 에이전트는 이렇게 묻는다 (kg-eval-ai 질문 은행의 생성 규칙)

| 패턴                | 특징                                  | 예                                                                |
| ------------------- | ------------------------------------- | ----------------------------------------------------------------- |
| A1 명시적 개체·관계 | 라벨·관계 타입을 지정한 정형 질의     | "Task 483 과 REFERENCES·RELATES_TO 로 연결된 Task 와 담당 Person" |
| A2 multi-hop 경로   | 두 개체 사이 연결 경로 요구           | "Concept 'API Gateway' 와 Wiki 문서 사이의 연결 경로"             |
| A3 집계             | 건수·분포·상위 N                      | "Person 별 담당 Task 수 상위 5명"                                 |
| A4 근거 id 요구     | 후속 호출에 쓸 노드 id·출처 명시 요구 | "각 결과에 노드 id 와 출처 문서를 포함해"                         |
| A5 체이닝           | 직전 답의 노드를 앵커로 후속 질의     | "위 결과 중 working 상태 Task 의 댓글 작성자"                     |

### 난이도 체계 (두 은행 공통 — 쉬운 질문부터 복잡한 질문까지)

질문 은행은 아래 5단계 난이도를 모두 포함해야 한다.
쉬운 질문은 기초 결함 검출기, 복잡한 질문은 그래프의 존재 이유 검증기다.

| 난이도           | 정의                                        | 예                                   |
| ---------------- | ------------------------------------------- | ------------------------------------ |
| L1 단순 조회     | 노드 1개 찾기 (문서 위치·담당자·속성)       | "OCR 개발 컨벤션 문서 어디 있지?"    |
| L2 1-hop         | 앵커에서 관계 1개 따라가기                  | "traceId 추적 관련 문서·업무 있어?"  |
| L3 multi-hop     | 2~3-hop, 여러 근거를 관계로 엮기            | "GPU 부족해서 했던 작업들 뭐야?"     |
| L4 인과·히스토리 | 결정·선후·원인 체인 재구성                  | "게이트웨이 뺀 거 왜 그랬지?"        |
| L5 종합·비교     | 여러 서브그래프를 분류·타임라인·비교로 종합 | "굵직한 장애들 원인 유형별로 나눠줘" |

- 은행 최소 구성: 12문항 이상, L1·L2 각 2 이상, L3 3 이상, L4 2 이상, L5 2 이상.
- 리포트는 전체 PASS·FAIL 집계와 함께 **난이도별 PASS/FAIL 분포**를 반드시 병기한다.
- L1~L2 에서 감점이 나면 즉시 원인 분석한다 — 쉬운 질문 실패는 앵커·사전·적재의 기초 결함 신호다.

## 3. 검색 품질 채점표 — 축별 독립 판정

두 채점자가 독립적으로 채점해도 같은 판정이 나오도록, 판정 대상·수치 경계·예외를 명시한다.

### 왜 합산 점수를 쓰지 않는가 (실측 근거)

이전 방식은 5축을 10점으로 합산했다(A2+R3+P2+G2+U1).
파일럿 34문항 실측에서 그 방식의 결함이 드러났다.

| 점수 | 문항 수 |
| --- | --- |
| 10 | 13 |
| 9 | 5 |
| 8 | 5 |
| 7 | 3 |
| 6 | 1 |
| 5 | **0** |
| 4 | 5 |
| 3 | **0** |
| 2 | 2 |
| 1 | **0** |

결정적 근거는 **최저점이 2점이라는 것**이다.
H-02·A-02 는 답을 사실상 찾지 못한 문항인데도 2점을 받았다 — 답이 없으면 인용할 것도 없어 환각이 불가능하므로 P(무환각) 2점을 그대로 받았기 때문이다.
즉 **실패한 답에도 만점을 주는 축이 합산에 섞여 하한을 떠받쳤다.**

같은 이유로 점수의 해상도도 낮다. 5·3·1점이 하나도 없이 8~10 구간과 2~4 구간으로 양극화됐다.
합산 점수는 "무엇이 실패했는가" 를 숫자에 묻어 버리고, 하한이 떠받쳐진 만큼 통과선의 의미도 왜곡한다.
축별로 판정하면 실패 축이 판정에 그대로 드러나고, U 처럼 정답성과 무관한 축을 정답 판정에서 분리할 수 있다.

축별 독립 판정으로 전환하면 원인이 판정에서 바로 읽히고, 임의의 합산 통과선을 정할 필요가 없어진다.
검색·RAG 품질 평가의 표준적 접근(faithfulness·context recall·answer relevancy 등)도 축을 합산하지 않고 각각 본다.

### 축별 판정 기준

| 축 | 판정 대상 | 값 | 통과 기준 |
| --- | --- | --- | --- |
| A 앵커 해석 | 질문의 지칭이 gold 근거 도출에 필요한 앵커 노드로 resolve 됐는가.<br>판정 방법: 응답 evidence(또는 cypher 가 매칭한 노드)에 앵커 포함 여부 | 전부 / 일부 / 전무 | **전부** |
| R 근거 재현율 | gold 를 **필수(required)** 와 **보강(supporting)** 으로 나눠 따로 판정한다 (아래 "R 축 상세" 참조).<br>expectedFacts 는 답변 텍스트에 그 사실이 담겼는지로 판정한다(동의어 표현 허용) — "왜" 질문의 사유 문장 자체를 검증한다 | 필수: 인용 건수 / 보강: 비율 | **필수 전부, 보강 ≥ 기준** |
| P 무환각 | 원본에 존재하지 않는 업무 번호·문서 제목·사람·수치를 인용했는가 | 위반 건수 | **0건** |
| G 그래프 정합 | 답변의 관계 주장(원인·담당·연결·순서·분류)에서 대표 주장 최대 3개를 뽑아 각각 Cypher 로 재현.<br>관계 주장이 없는 L1 단순 조회는 "결과 노드가 그래프에 존재하는가"로 대체한다.<br>순서(타임라인)·분류 주장(L5)의 옳고 그름도 이 축에서 검증한다 | 재현 비율 | **100%** |
| U 행동 유용성 | 행동 가능한 참조(업무 번호·위키 제목·코드 위치·담당자 이름)가 1개 이상 있고 그 참조가 정확한가 | 있음 / 없음 | 있음 (**권고** — 미달은 경고로 기록하고 실패로 보지 않는다) |

### R 축 상세 — 필수·보강 분리

비율 기준은 작은 gold 집합에서 반드시 이산화된다.
gold 가 1개면 비율은 0% 또는 100% 뿐이므로, 어떤 임계값을 써도 "누락 0개" 요구가 된다.
실측: tc-ocr 34문항의 gold 규모는 최대 7개이고 10개 이상인 문항이 0개다 — 비율 90%든 70%든 전 문항에서 누락 허용이 0개였다.

gold 항목의 중요도가 균일하지 않다는 점이 문제의 뿌리다.
예를 들어 타임라인 질문 H-12 의 gold 7개 중 `491(장애)→483(제거 결정)→498(등가성 검증)` 은 답의 핵심이고,
`504·505·506`(공인 전환 후속)은 하나가 빠져도 답이 틀린 것은 아니다.

그래서 gold 를 두 등급으로 나눈다 (검색 평가의 graded relevance 와 같은 발상).

| 등급 | 의미 | 판정 |
| --- | --- | --- |
| **필수 (required)** | 이것을 빠뜨리면 답이 틀린 것 | **전부 인용해야 통과** — 무결점 요구가 정당하다 |
| **보강 (supporting)** | 있으면 답이 풍부해지지만 없어도 답은 성립 | **비율 기준** (파일럿 ≥ 40% / 인수 ≥ 60%) |

- gold JSON 에 `required` 와 `supporting` 을 나눠 적는다. 등급 표기가 없는 기존 gold 는 전부 `required` 로 간주하지 않고, **필수/보강 재분류를 먼저 수행한 뒤 판정한다**.
- 보강 항목이 0개인 문항은 필수 판정만 한다 (비율 기준을 적용하지 않는다).
- `groundTruthCypher` 가 있는 질문은 R 을 **ground truth 결과 행 대비 일치율**로 계산하고, 필수/보강 분리를 적용하지 않는다. gold 가 함께 있으면 gold 는 evidence 확인용 보조로만 쓴다 (판정 주체는 ground truth 다).
- 등급 부여 기준 — 질문에 답하는 데 **인과·순서·결론의 핵심 고리**인 항목이 필수다. 같은 사실을 여러 근거가 뒷받침할 때는 그중 하나만 필수로 두고 나머지를 보강으로 둔다.

### 판정 규칙

- **문항 판정**: A·R·P·G 를 전부 통과하면 PASS. 하나라도 미달이면 FAIL 이고, **미달 축을 함께 기록**한다 (예: `FAIL(A)`, `FAIL(R 필수 2/3)`).
- **세트 판정**: 전 문항 PASS 여야 통과다. FAIL 문항은 미달 축별로 집계해 개선 루프 입력으로 쓴다.
- **채점 순서**: 답변 텍스트만으로 A·R·P·U 를 먼저 판정하고 G 는 마지막에 Cypher 검증으로 판정한다.
- **경계 처리**: 애매하면 항상 미달로 판정한다 (엄격 우선 — 판정 인플레이션 방지).
- U 를 권고로 두는 이유 — 정답성과 근거가 먼저이고, 유용성은 그다음이다. 다만 U 미달이 반복되면 답변 합성 프롬프트를 손볼 신호로 본다.

### 이전 합산 점수와의 관계

- 이전 리포트의 세트 점수(예: human 161/180)는 새 기준과 **비교할 수 없다**. 척도가 다르다.
- rubric 개정 후 첫 평가에서 기존 세트를 새 기준으로 재측정해 기준선을 다시 만든다.
- 재측정 결과는 문항별 축 판정 표로 리포트에 남긴다 — 회귀 판정에 문항별 기준선이 필요하다.

## 4. 통과 조건

| 시점 | A | R 필수 | R 보강 | P | G | 정적 기준 (섹션 1) |
| --- | --- | --- | --- | --- | --- | --- |
| 파일럿 (새 소스 첫 통합) | 전부 | 전부 | ≥ 40% | 0건 | 100% | S1·S6 필수, 나머지 측정·기록 |
| 인수 (전량) | 전부 | 전부 | ≥ 60% | 0건 | 100% | S1·S6 통과, S2·S3·S5 측정·기록 |
| 일반화 루프 (새 프로젝트·새 저장소) | 전부 | 전부 | ≥ 60% | 0건 | 100% | 인수와 동일 |

- **필수 항목·A·P·G 는 시점과 무관하게 동일하다.** 앵커 실패·환각·관계 오류·핵심 근거 누락은 어느 단계에서도 허용하지 않는다.
- 단계 차이는 **보강 비율에서만** 둔다 — 파일럿은 추출·적재가 미완이라 보강 근거가 부분적으로만 그래프에 있다.
- 정적 기준의 S2·S3·S5 를 "측정·기록" 으로 둔 이유: `static-checks.cypher` 의 S3 는 `dictMatched`·`origin` 을 읽는데 적재기가 이 속성을 기록하지 않아 현재 측정 불가이고, S2 는 절대 기준 `< 5%` 가 현 그래프에서 이미 초과 상태다. 두 항목은 측정식 정밀화가 선행돼야 통과 판정을 걸 수 있다 (백로그).
- S7(질문 의도 커버리지)은 `static-checks.cypher` 에 쿼리가 없다 — 질문 세트의 의도 유형 커버리지로 대체 판정하고, 쿼리화는 백로그로 둔다.

난이도 구성 요건 (통과 조건과 별개로 충족해야 한다):

- 질문 세트는 L1~L5 최소 구성(섹션 2)을 충족해야 한다 — 쉬운 질문만 넣어 기준을 맞추는 우회를 막는다.
- L4~L5 문항도 같은 통과 조건을 적용한다. 미달 시 질문을 쉽게 바꾸지 말고 엔진·추출을 개선한다.
- 리포트는 난이도별 PASS/FAIL 분포를 반드시 병기한다.

## 5. 미달 시 개선 루프

1. FAIL 문항을 **미달 축으로 분류**한다. 축별 원인 대응:

| 미달 축 | 주요 원인 | 손볼 곳 |
| --- | --- | --- |
| A | 앵커 실패 | Concept 사전·fulltext 인덱스·용어 변형 |
| R | 근거 누락 | 추출 프롬프트·구조 추출기·스키마 커버리지 |
| R (구조 소스) | 추출 누락 | 구조 파서(YAML·매니페스트) |
| P | 환각 | 답변 합성 프롬프트·근거 제한 |
| G | 경로 부재 또는 관계 오류 | 온톨로지 커버리지·Cypher 생성 규칙 |

2. 가장 많은 축 하나만 고치고 재평가한다 — 한 번에 여러 축을 고치면 회귀 원인을 알 수 없다.
3. 리포트를 `eval/reports/<날짜>-<stage>.md` 에 남긴다: 문항별 축 판정 표, FAIL 목록, 미달 축 집계, 적용한 수정.
4. 통과까지 반복한다. **종료 조건**:
   - 같은 축을 3회 고쳐도 미달이면 온톨로지 설계 재검토로 승격한다.
   - 루프 5회에 도달하면 반복을 멈추고, 미달 문항 목록·미달 축·필요한 설계 변경을 리포트로 정리해 **사용자 판정을 받는다**. 무한 반복을 막는 상한이다.

## 6. gold set 부트스트랩 (새 프로젝트에 루프를 확장할 때)

1. 새 프로젝트 색인 후, 태그 분포·최근 업무 30건·위키 트리를 훑어 그 프로젝트의 핵심 사건·시스템을 파악한다.
2. 섹션 2의 H1~H5·A1~A5 패턴별 최소 1문항과 난이도 L1~L5 최소 구성(12문항 이상)을 모두 충족하게 질문을 만든다.
3. 각 질문의 기대 근거(업무 번호·위키 제목)를 원본 데이터에서 직접 확인해 gold 로 기록한다 — 그래프를 보고 만들면 순환 검증이 된다.
4. `eval/questions-human-<project>.json`, `eval/questions-ai-<project>.json` 으로 저장한다.
