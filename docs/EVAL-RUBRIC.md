# 지식그래프 품질 rubric — 온톨로지 기준·질문 역설계·채점표

품질 게이트의 단일 소스다.
평가 스킬(`kg-eval-human`, `kg-eval-ai`)이 이 문서의 채점표와 통과선을 따르고,
stage commit 마다 실행해 점수가 통과선을 넘을 때까지 개선 루프를 돈다.

## 1. 온톨로지 정적 기준 (그래프 자체의 높은 기준)

질의와 무관하게 적재된 그래프가 항상 충족해야 하는 기준.
Cypher 한 줄로 측정 가능해야 하며, 파일럿(Phase 2)부터 매 평가에 포함한다.

| #   | 기준               | 측정                                                            | 통과선 |
| --- | ------------------ | --------------------------------------------------------------- | ------ |
| S1  | 스키마 정합        | 온톨로지 계약 밖 라벨·관계 수                                   | 0      |
| S2  | Concept 응집       | 정규화 후 중복 의심 Concept(편집거리·부분포함 근사 중복) 비율   | < 5%   |
| S3  | 사전 적중          | LLM 이 만든 Concept 중 표준 사전(canonical+alias)에 매칭된 비율 | ≥ 80%  |
| S4  | 연결성             | 고아 Task(CONTAINS 외 관계 0) 비율                              | < 10%  |
| S5  | 추출 밀도          | Task 당 평균 MENTIONS 관계 수                                   | ≥ 1.5  |
| S6  | 근거 추적          | LLM 생성 노드·관계 중 출처 문서 id(sourceDocId) 보유 비율       | 100%   |
| S7  | 질문 의도 커버리지 | 아래 6개 의도 유형별로 답을 표현할 스키마 경로 존재             | 6/6    |

의도 유형 (S7): 원인·히스토리 / 담당·사람 / 문서·참고 / 의존·구조 / 상태·진행 / 집계·통계.

## 2. 질문 방식 역설계

### 사람은 이렇게 묻는다 (kg-eval-human 질문 은행의 생성 규칙)

| 패턴                    | 특징                                                   | 예 (tc-ocr)                           |
| ----------------------- | ------------------------------------------------------ | ------------------------------------- |
| H1 모호한 지칭          | 대상을 이름 대신 사건·맥락으로 지칭                    | "게이트웨이 뗀 거 왜 그랬지?"         |
| H2 별칭·부분 이름       | 공식 명칭 대신 줄임말·구어                             | "모델서버 죽었을 때 볼 문서 뭐 있지?" |
| H3 상대 시간            | 절대 날짜 없이 최근·작년·저번                          | "최근에 부하테스트 관련해서 뭐 했지?" |
| H4 행동 지향            | 답을 받아 다음 행동(코드 위치·담당자·문서)으로 가려 함 | "쿠콘 장애 나면 어디 코드 봐야 해?"   |
| H5 짧은 질문, 깊은 기대 | 질문은 한 줄이지만 답은 multi-hop 이어야 함            | "GPU 부족해서 했던 작업들 뭐야?"      |

### AI 에이전트는 이렇게 묻는다 (kg-eval-ai 질문 은행의 생성 규칙)

| 패턴                | 특징                                  | 예                                                                |
| ------------------- | ------------------------------------- | ----------------------------------------------------------------- |
| A1 명시적 개체·관계 | 라벨·관계 타입을 지정한 정형 질의     | "Task 483 과 REFERENCES·RELATES_TO 로 연결된 Task 와 담당 Person" |
| A2 multi-hop 경로   | 두 개체 사이 연결 경로 요구           | "Concept 'API Gateway' 와 Wiki 문서 사이의 연결 경로"             |
| A3 집계             | 건수·분포·상위 N                      | "Person 별 담당 Task 수 상위 5명"                                 |
| A4 근거 id 요구     | 후속 호출에 쓸 노드 id·출처 명시 요구 | "각 결과에 노드 id 와 출처 문서를 포함해"                         |
| A5 체이닝           | 직전 답의 노드를 앵커로 후속 질의     | "위 결과 중 working 상태 Task 의 댓글 작성자"                     |

### 난이도 체계 (두 은행 공통 — 쉬운 질문부터 복잡한 질문까지)

질문 은행은 아래 5단계 난이도를 모두 포함해야 한다.
쉬운 질문은 기초 결함 검출기, 복잡한 질문은 그래프의 존재 이유 검증기다.

| 난이도           | 정의                                        | 예                                   |
| ---------------- | ------------------------------------------- | ------------------------------------ |
| L1 단순 조회     | 노드 1개 찾기 (문서 위치·담당자·속성)       | "OCR 개발 컨벤션 문서 어디 있지?"    |
| L2 1-hop         | 앵커에서 관계 1개 따라가기                  | "traceId 추적 관련 문서·업무 있어?"  |
| L3 multi-hop     | 2~3-hop, 여러 근거를 관계로 엮기            | "GPU 부족해서 했던 작업들 뭐야?"     |
| L4 인과·히스토리 | 결정·선후·원인 체인 재구성                  | "게이트웨이 뺀 거 왜 그랬지?"        |
| L5 종합·비교     | 여러 서브그래프를 분류·타임라인·비교로 종합 | "굵직한 장애들 원인 유형별로 나눠줘" |

- 은행 최소 구성: 12문항 이상, L1·L2 각 2 이상, L3 3 이상, L4 2 이상, L5 2 이상.
- 리포트는 세트 점수와 함께 **난이도별 점수**를 반드시 병기한다.
- L1~L2 에서 감점이 나면 즉시 원인 분석한다 — 쉬운 질문 실패는 앵커·사전·적재의 기초 결함 신호다.

## 3. 검색 품질 채점표 (질문당 10점)

두 채점자가 독립적으로 채점해도 같은 점수가 나오도록, 판정 대상·수치 경계·예외를 명시한다.

| 축            | 배점                      | 채점 기준                                                                                                                                                                                                                                                                                               |
| ------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A 앵커 해석   | 0~2                       | 판정 대상: 질문의 지칭이 gold 근거 도출에 필요한 앵커 노드로 resolve 됐는가.<br>판정 방법: 응답 evidence(또는 cypher 가 매칭한 노드)에 앵커 포함 여부.<br>2: 앵커 전부 / 1: 일부 / 0: 전무. 앵커가 1개인 질문은 2 아니면 0.                                                                             |
| R 근거 재현율 | 0~3                       | r = gold 근거(tasks·wikis·concepts·persons·**expectedFacts** 합집합) 중 답변·evidence 에 인용된 비율.<br>expectedFacts 는 답변 텍스트에 그 사실이 담겼는지로 판정(동의어 표현 허용) — "왜" 질문의 사유 문장 자체를 검증하는 축이다.<br>3: r=100% / 2: 50%≤r<100% / 1: 0<r<50% / 0: r=0.<br>groundTruthCypher 질문은 gold 대신 ground truth 결과 행 대비 일치율에 같은 경계 적용. |
| P 무환각      | 2 또는 0 (이진, 1점 없음) | 원본에 존재하지 않는 업무 번호·문서 제목·사람·수치를 1건이라도 인용하면 0 + 해당 질문 fail. 위반 없으면 2.                                                                                                                                                                                              |
| G 그래프 정합 | 0~2                       | 답변의 관계 주장(원인·담당·연결·순서·분류)에서 대표 주장 최대 3개를 뽑아 각각 Cypher 로 재현.<br>2: 전부 재현 / 1: 1개 이상 / 0: 전무.<br>관계 주장이 없는 L1 단순 조회는 "결과 노드가 그래프에 존재하는가"로 대체 (존재 2 / 부재 0).<br>순서(타임라인)·분류 주장(L5)의 옳고 그름도 이 축에서 검증한다. |
| U 행동 유용성 | 0~1                       | 행동 가능한 참조(업무 번호, 위키 제목, 코드 위치, 담당자 이름) 1개 이상 존재하고 그 참조가 정확하면 1, 아니면 0.                                                                                                                                                                                        |

- 세트 점수 = (질문별 점수 합 / 만점) × 100%. P 위반(fail) 질문 수는 별도 집계한다.
- 공통 규칙: 답변 텍스트만으로 A·R·P·U 를 먼저 채점하고 G 는 마지막에 Cypher 검증으로 채점한다.
  경계가 애매하면 항상 낮은 점수를 준다 (엄격 우선 — 점수 인플레이션 방지).

## 4. 통과선

| 시점                      | kg-eval-human | kg-eval-ai | 정적 기준 (섹션 1)        | 환각 fail |
| ------------------------- | ------------- | ---------- | ------------------------- | --------- |
| Phase 2 파일럿 (30건)     | ≥ 60%         | ≥ 70%      | S1·S6 필수, 나머지 측정만 | 0건       |
| Phase 3 인수 (전량)       | ≥ 75%         | ≥ 85%      | 7개 전부 통과             | 0건       |
| 일반화 루프 (새 프로젝트) | ≥ 70%         | ≥ 80%      | 7개 전부 통과             | 0건       |

ai 통과선이 더 높은 이유: 정형 질의는 anchor 모호성이 없어 낮은 점수는 곧 그래프·질의 엔진 결함이다.
새 프로젝트 통과선이 tc-ocr 인수선보다 5%p 낮은 이유: gold set 이 갓 부트스트랩된 상태의 측정 오차를 허용한다.

난이도 하위 기준 (세트 점수와 별개로 모두 충족해야 통과):

- Phase 3 인수·일반화 루프: L1~L2 문항 구간 점수 ≥ 90% — 쉬운 질문은 거의 만점이어야 한다.
- L4~L5 구간 점수가 세트 통과선보다 15%p 이상 낮으면, 세트가 통과여도 FAIL 로 본다 — 쉬운 질문으로 점수를 채우는 것을 막는다.

## 5. 점수 미달 시 개선 루프

1. 실패 질문별로 원인을 4개 중 하나로 분류한다:
   앵커 실패(사전·fulltext) / 근거 누락(추출 프롬프트·스키마) / 환각(답변 합성 프롬프트) / 경로 부재(온톨로지 커버리지).
2. 분류 결과가 가장 많은 축 하나만 고치고 재평가한다 — 한 번에 여러 축을 고치면 회귀 원인을 알 수 없다.
3. 리포트를 `eval/reports/<날짜>-<stage>.md` 에 남긴다: 점수표, fail 목록, 원인 분류, 적용한 수정.
4. 통과선 도달까지 반복. 같은 축을 3회 고쳐도 미달이면 온톨로지 설계 재검토로 승격한다.

## 6. gold set 부트스트랩 (새 프로젝트에 루프를 확장할 때)

1. 새 프로젝트 색인 후, 태그 분포·최근 업무 30건·위키 트리를 훑어 그 프로젝트의 핵심 사건·시스템을 파악한다.
2. 섹션 2의 H1~H5·A1~A5 패턴별 최소 1문항 + 난이도 L1~L5 최소 구성(12문항 이상)을 모두 충족하게 질문을 만든다.
3. 각 질문의 기대 근거(업무 번호·위키 제목)를 원본 데이터에서 직접 확인해 gold 로 기록한다 — 그래프를 보고 만들면 순환 검증이 된다.
4. `eval/questions-human-<project>.json`, `eval/questions-ai-<project>.json` 으로 저장한다.
