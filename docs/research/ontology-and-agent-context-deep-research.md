# 온톨로지와 AI 에이전트 컨텍스트 심층 조사

작성일: 2026-07-28

대상:

- 온톨로지를 만들고 지속적으로 다듬는 방법을 학습하려는 개발자
- 지식그래프를 사람과 AI 에이전트가 함께 쓰게 만들려는 팀
- 코딩 에이전트에 저장소·문서·업무 컨텍스트를 공급하려는 설계자
- 현재 `devloop-v2` Dooray 지식그래프를 다음 단계로 발전시키려는 실험

## 먼저 읽을 결론

온톨로지는 세계를 완전하게 복제하는 분류표가 아니다.

다음 네 가지를 안정적으로 연결하는 변경 가능한 계약이다.

1. 사용자가 실제로 묻는 질문
2. 답을 만들 때 따라갈 수 있는 개념과 관계
3. 답을 뒷받침하는 원본 근거
4. 사람이 검토하거나 시스템이 실행할 수 있는 행동

따라서 좋은 온톨로지의 목표는 노드 수나 관계 수를 늘리는 것이 아니다.
필요한 질문을 더 정확하게 답하고, 잘못된 결합을 막고, 변경의 영향을 설명하는 것이다.

이번 조사에서 가장 일관되게 확인된 운영 원칙은 다음과 같다.

- 질문에서 시작한다.
  자연어 역량 질문을 먼저 만들고 이를 그래프 질의와 회귀 검사로 변환한다.
- 구조적으로 얻을 수 있는 사실과 추론한 주장을 분리한다.
  LLM의 출력은 사실이 아니라 출처가 붙은 후보 주장으로 취급한다.
- 개체 동일성과 문자열 유사성을 혼동하지 않는다.
  병합은 같은 대상을 가리킨다는 증거가 있을 때만 수행한다.
- 폐기는 삭제보다 비활성화를 우선한다.
  식별자, 정의, 대체 대상, 폐기 이유, 이전 경로를 남긴다.
- 온톨로지 품질과 검색·답변 품질을 따로 측정한다.
  논리적으로 깔끔한 온톨로지가 유용한 답을 보장하지 않으며, 좋은 답변 몇 개가 온톨로지 정합성을 보장하지도 않는다.
- 사람용 화면과 에이전트용 인터페이스는 같은 의미 계층을 공유하되 표현은 다르게 만든다.
  사람은 설명·탐색·비교가 필요하고, 에이전트는 안정적인 식별자·작은 근거 묶음·권한·최신성 정보가 필요하다.
- 컨텍스트는 미리 전부 넣지 않는다.
  지속 지침, 의미 계층, 원본 근거, 실시간 상태, 작업 기억을 분리하고 필요한 순간에 조립한다.
- 컨텍스트 제공자는 단순 검색 API가 아니다.
  검색, 권한 검사, 최신성 판정, 중복 제거, 토큰 예산, 인용, 실행 추적을 포함하는 경계다.

현재 `devloop-v2`는 이미 좋은 출발점을 갖고 있다.

- 고정 스키마를 코드 계약으로 관리한다.
- 구조 추출과 LLM 추출을 분리한다.
- LLM 생성 항목에 `sourceDocId`를 강제한다.
- 사람 질문과 AI 질문을 별도 은행으로 평가한다.
- 개념 파편화와 근거 도달성을 실측한다.

다음 단계는 OWL로 전면 이주하는 것이 아니다.

우선 다음 세 가지를 추가하는 편이 학습 효과와 품질 개선 가능성이 크다.

1. 역량 질문과 연결된 온톨로지 변경 절차
2. 개념·관계 후보의 승인, 비활성화, 대체, 출처 이력
3. 코딩 에이전트가 근거 묶음을 요청하는 읽기 전용 컨텍스트 제공자

## 개념을 먼저 분리한다

### 분류 체계

상위·하위 또는 범주 관계를 중심으로 용어를 정리한다.

예:

```text
OCR
└── Document OCR
    ├── ID Card OCR
    └── Business Registration OCR
```

검색 필터, 메뉴, 태그 정리에 유용하지만 관계의 의미와 제약을 충분히 표현하지는 않는다.

### 온톨로지

도메인에서 사용하는 개념, 관계, 속성, 제약, 정의를 명시한 의미 계약이다.

W3C의 [OWL 2 입문서](https://www.w3.org/TR/owl2-primer/)는 온톨로지를 클래스, 속성, 개체, 데이터 값과 이들 사이의 공리를 통해 표현한다.
OWL은 선언적 의미와 추론에 강하지만 데이터가 반드시 존재해야 한다는 입력 검증 언어는 아니다.

### 지식그래프

온톨로지 또는 느슨한 스키마에 따라 실제 개체와 관계를 연결한 데이터다.

온톨로지가 “어떤 종류의 것이 어떤 관계를 가질 수 있는가”를 말한다면,
지식그래프는 “Task 483이 API Gateway 제거 결정을 포함한다” 같은 구체적 진술을 담는다.

### 검증 형태

[SHACL](https://www.w3.org/TR/shacl/)은 RDF 그래프가 요구 형태를 만족하는지 검증한다.

실무에서는 다음 구분이 중요하다.

- OWL: 무엇이 논리적으로 참이거나 추론 가능한가?
- SHACL 또는 애플리케이션 스키마: 입력 데이터가 요구 구조를 만족하는가?

`devloop-v2`는 RDF·OWL 시스템이 아니라 Neo4j 속성 그래프다.
그러므로 OWL을 도입하지 않아도 Zod, TypeScript 상수, Cypher 정적 검사로 SHACL과 유사한 검증 규율을 적용할 수 있다.

### 컨텍스트

모델이 현재 작업을 수행할 때 사용할 수 있도록 선택되고 조립된 정보다.

컨텍스트는 지식그래프 전체와 같지 않다.
그래프에서 찾은 근거, 저장소 파일, 작업 지침, 대화 이력, 명령 출력, 권한 정보 중 현재 작업에 필요한 일부다.

### 메모리

여러 작업 또는 세션에 걸쳐 다시 사용할 가능성이 있는 컨텍스트다.

메모리는 다음을 섞으면 안 된다.

- 사람이 승인한 지속 규칙
- 에이전트가 자동으로 추출한 관찰
- 작업 중 잠시 필요한 상태
- 변경 가능한 외부 시스템의 현재 값

승인 규칙은 저장소 문서에 두고,
자동 기억은 회상 보조 계층으로 두며,
실시간 값은 호출할 때 다시 가져와야 한다.

## 온톨로지를 만드는 검증 가능한 절차

### 사용 목적과 경계를 한 문단으로 고정한다

다음 질문에 한 문장씩 답한다.

- 어떤 도메인을 다루는가?
- 누가 사용하고 누가 유지하는가?
- 어떤 질문에 답해야 하는가?
- 어떤 결정 또는 행동을 지원하는가?
- 무엇은 명시적으로 다루지 않는가?

[Ontology Development 101](https://protege.stanford.edu/publications/ontology_development/ontology101.pdf)은 도메인, 용도, 답해야 할 질문, 사용자와 유지관리자를 먼저 정하도록 권한다.

경계 문장이 없으면 온톨로지는 관련 있어 보이는 명사를 계속 흡수한다.
이 상태에서는 “더 넣을 것인가”는 결정할 수 있어도 “충분한가”와 “빼야 하는가”는 결정할 수 없다.

### 역량 질문을 만든다

역량 질문은 온톨로지가 답해야 하는 자연어 질문이다.

예:

- API Gateway 제거를 결정한 업무와 근거 댓글은 무엇인가?
- 이 결정을 검증하기 위해 뒤따른 업무는 무엇인가?
- 특정 컴포넌트에 영향을 주는 아직 유효한 결정은 무엇인가?
- 이 관계는 어떤 원문과 추출 버전에서 왔는가?

질문은 단순 조회부터 비교·인과·시간 순서까지 난이도를 나눈다.
각 질문에는 다음을 연결한다.

- 필요한 개념과 관계
- 정답으로 인정할 식별자
- 필수 근거와 보조 근거
- 허용하지 않을 추론
- 실행 가능한 그래프 질의

역량 질문을 회귀 검사로 쓰는 접근은
[역량 질문에서 저작 검사를 만드는 연구](https://researchportal.port.ac.uk/en/publications/computing-authoring-tests-from-competency-questions-experimental-/)에서
실험적으로 구체화됐다.

### 용어 목록보다 사례 문장을 먼저 수집한다

도메인 전문가가 실제로 쓰는 문장과 질문에서 다음 후보를 표시한다.

- 독립적으로 식별할 대상
- 여러 대상이 공유하는 유형
- 대상 사이의 관계
- 시간에 따라 바뀌는 상태
- 출처가 필요한 주장
- 사람이 수행하거나 시스템이 실행하는 행동

명사라고 모두 클래스가 되는 것은 아니다.
동사라고 모두 관계가 되는 것도 아니다.

판단 기준은 해당 요소가 질문, 제약, 추론, 권한, 행동에서 독립적으로 필요하냐는 것이다.

### 기존 어휘와 패턴을 먼저 찾는다

새 용어를 만들기 전에 다음을 확인한다.

- 동일 도메인의 공개 온톨로지
- 널리 쓰이는 상위 온톨로지
- 출처를 표현하는 [PROV-O](https://www.w3.org/TR/prov-o/)
- 시간, 단위, 지리, 사람, 조직 등 검증된 공통 어휘
- 반복되는 온톨로지 설계 패턴

NeOn 방법론은 고립된 온톨로지를 처음부터 만드는 한 가지 절차보다,
기존 온톨로지·비온톨로지 자원·모듈·정렬을 조합하는 여러 시나리오를 제시한다.
개요와 원 자료는 [NeOn 자료 저장소](https://research-archive.stem.open.ac.uk/neon/dissemination/)와
[NeOn 방법론 논문](https://research.uni-sofia.bg/bitstream/10506/672/1/S3T2009_24_AGomez-Perez_MCSuarez-Figueroa.pdf)에서 볼 수 있다.

재사용은 이름을 복사하는 것이 아니다.

- 의미가 정말 같은가?
- 식별자가 안정적인가?
- 라이선스와 변경 정책이 맞는가?
- 필요한 일부만 모듈로 가져올 수 있는가?
- 외부 버전 변경이 우리 질문을 깨뜨릴 수 있는가?

를 확인해야 한다.

### 작고 연결된 핵심 모델을 만든다

처음부터 모든 속성과 예외를 모델링하지 않는다.
역량 질문을 답하는 데 필요한 가장 작은 연결 경로를 만든다.

권장 순서는 다음과 같다.

1. 안정적인 개체 식별자
2. 핵심 유형
3. 방향이 명확한 관계
4. 출처와 시간
5. 반드시 지켜야 할 제약
6. 필요한 경우에만 더 강한 논리 공리

클래스 계층은 “모든 A는 B인가?”라는 문장이 자연스럽고 참일 때만 사용한다.
이 규칙은 OWL 2 입문서의 실용적 설명과 같다.

### 구조적 사실, 추출 주장, 해석을 분리한다

예를 들어 Dooray 데이터에서 다음은 구조적 사실이다.

- 업무 번호
- 작성자와 담당자
- 댓글 소속
- 명시적 업무 참조
- 태그

다음은 추출된 주장이다.

- 어떤 업무가 특정 기술 개념을 언급한다.
- 두 컴포넌트가 의존한다.
- 어떤 댓글이 의사결정의 근거다.
- 어떤 업무가 다른 업무의 후속이다.

다음은 답변 시점의 해석이다.

- 이 장애가 제거 결정의 직접 원인이었다.
- 이 문서가 지금도 가장 적절한 대응 절차다.

세 층을 같은 관계로 저장하면 신뢰도, 오류 수정, 시간 변화, 책임 소재를 설명하기 어려워진다.

최소한 추출 주장에는 다음을 기록한다.

```text
sourceId
sourceRevision
extractionMethod
extractorVersion
observedAt
confidence
status
```

중요하거나 충돌 가능한 주장은 관계 속성보다 `Claim` 노드로 승격하는 편이 낫다.
그러면 한 주장에 여러 근거, 반대 근거, 검토 상태, 유효 기간을 붙일 수 있다.

### 제약과 실패 사례를 먼저 작성한다

좋은 제약은 정상 예시만큼 반례를 구체적으로 갖는다.

예:

- `Decision EVIDENCED_BY Comment`는 가능하다.
- 출처 문서에 없는 댓글 식별자를 만들어서는 안 된다.
- `Gateway API`와 `API Gateway`는 토큰이 같아도 같은 개체가 아니다.
- `Document`와 `Document.Console`은 문자열 포함 관계만으로 병합하지 않는다.

OWL 추론을 사용할 경우 논리 일관성과 의도치 않은 함의를 검사한다.
속성 그래프에서는 다음을 정적 검사로 만든다.

- 허용하지 않은 라벨·관계
- 허용하지 않은 시작·종료 라벨 조합
- 필수 속성 누락
- 고아 노드
- 출처 없는 추출 관계
- 폐기된 개념을 가리키는 활성 관계
- 방향이나 관계 종류가 질문 계약과 어긋나는 경로

### 실제 데이터와 실제 질문으로 파일럿한다

전체 데이터를 적재하기 전에 대표 문서 묶음을 고른다.

다음 사례가 모두 포함돼야 한다.

- 쉬운 명시 관계
- 여러 문서를 잇는 질문
- 같은 문자열의 다른 의미
- 같은 개체의 여러 별칭
- 시간에 따라 바뀐 결정
- 근거가 아예 없는 질문
- LLM이 과잉 추론하기 쉬운 문장

통과율만 보면 안 된다.
실패를 다음 원인으로 분해한다.

- 원천 데이터 부재
- 추출 누락
- 개체 해소 실패
- 온톨로지 경로 부재
- 질의 생성 실패
- 컨텍스트 조립 실패
- 답변 합성 실패
- 평가 정답 오류

### 변경을 제안, 검토, 이전, 배포한다

온톨로지 변경을 코드 변경처럼 다룬다.

각 변경 제안에는 다음을 포함한다.

- 변경 이유와 연결된 역량 질문
- 추가, 수정, 병합, 분리, 비활성화 대상
- 기존 질의와 데이터에 미치는 영향
- 이전 규칙
- 되돌리기 방법
- 담당 검토자
- 배포 버전

[온톨로지 진화 조사](https://doi.org/10.1017/S0269888913000349)는 버전 저장만으로 충분하지 않으며,
의존하는 온톨로지·응용 프로그램·에이전트에 미치는 영향을 함께 관리해야 한다고 정리한다.

## 무엇을 추가할 것인가

다음 조건을 모두 만족하는 후보만 정식 온톨로지에 넣는다.

### 질문 또는 행동에 쓰인다

다음 중 하나가 구체적으로 있어야 한다.

- 이 개념 때문에 새 질문에 답할 수 있다.
- 기존 질문의 모호성을 줄인다.
- 권한 또는 검증 제약을 표현한다.
- 사람이 수행할 행동이나 에이전트 도구 호출을 제한한다.
- 변경 영향을 추적한다.

“언젠가 유용할 것 같다”는 정식 편입 근거가 아니다.
그런 항목은 후보 어휘에 둔다.

### 독립적인 정체성이 있다

다른 개체와 구분할 안정적인 식별 기준이 있어야 한다.

예:

- Dooray 업무 번호
- 위키 페이지 ID
- 저장소의 커밋과 심볼 위치
- 조직이 관리하는 제품 식별자

이름만 있고 동일성 기준이 없으면 별칭 또는 검색어일 가능성이 높다.

### 정의와 사용 예가 있다

최소 문서 항목은 다음과 같다.

- 사람이 읽는 정의
- 포함 예
- 제외 예
- 상위 범위
- 허용 관계
- 소유자
- 출처

### 데이터 품질을 감당할 수 있다

새 관계를 추가하기 전에 확인한다.

- 원천에 충분한 단서가 있는가?
- 구조적으로 얻을 수 있는가?
- LLM 추출 정밀도와 재현율을 측정할 수 있는가?
- 오탐이 답변에 주는 피해는 무엇인가?
- 사람이 검토할 수 있는 양인가?

추출이 불안정한 관계는 정식 사실보다 후보 주장으로 저장한다.

## 무엇을 병합하고 무엇을 분리할 것인가

### 병합은 동일성 판단이다

두 개념이 자주 함께 나오거나 문자열이 비슷하다는 것은 병합 근거가 아니다.

병합을 승인하려면 다음 증거를 조합한다.

- 동일한 외부 식별자
- 도메인 소유자의 확인
- 정의와 범위의 일치
- 서로 대체해도 역량 질문의 의미가 변하지 않음
- 시간에 따른 공식 개명
- 출처 문서에서 명시한 동의어

병합 시에는 하나의 정식 식별자를 남기고 다른 이름을 별칭으로 보존한다.
이미 공개된 식별자는 삭제하지 않고 대체 관계를 남긴다.

### 분리는 다의성과 범위 충돌을 해결한다

다음 신호가 있으면 하나의 개념을 분리한다.

- 같은 이름이 서로 다른 제품 또는 팀에서 다른 대상을 가리킨다.
- 관계의 시작·종료 유형이 함께 성립할 수 없다.
- 속성이나 생명주기가 크게 다르다.
- 검색 결과에서 서로 무관한 근거가 반복해서 섞인다.
- 도메인 전문가가 별도 식별을 요구한다.

`devloop-v2`의 `Gateway API`와 `API Gateway`,
일반 `Document`와 컴포넌트 `Document.Console`은 이 원칙을 보여주는 실측 반례다.

### 상위·하위와 별칭을 혼동하지 않는다

다음은 대개 병합 대상이 아니다.

- `OCR`과 `신용카드 OCR`
- `NHN Cloud`와 `NHN Cloud Log & Crash`
- `ingress`와 `ingress-nginx`
- `user`와 `service user`

짧은 이름이 긴 이름의 일부라고 같은 개체가 되지 않는다.
상위·하위 관계가 필요하면 명시적으로 모델링한다.

## 무엇을 뺄 것인가

먼저 “어디에서 뺄 것인가”를 구분한다.

| 판단 | 온톨로지 | 저장 데이터 | 기본 컨텍스트 | 사용 조건 |
| --- | --- | --- | --- | --- |
| 핵심 활성 | 유지 | 유지 | 필요하면 포함 | 현재 질문·제약·행동에 직접 사용한다. |
| 활성 저빈도 | 유지 | 유지 | 제외하고 호출 시 회수 | 드물지만 보안·장애·법적 가치가 있거나 특정 질문에 필요하다. |
| 대체됨 | 비활성화하고 대체 관계 유지 | 이전 기간 데이터 보존 | 기본 제외 | 새 개념으로 이전됐지만 옛 참조 해석에 필요하다. |
| 검증 대기 | 후보 영역에 유지 | 근거와 함께 격리 | 기본 제외 | 자동 추출됐으나 아직 동일성·정확성이 검증되지 않았다. |
| 오류·민감 유출 | 계약에서 제거 | 정책에 따라 물리 삭제 | 즉시 제외 | 보존 자체가 잘못됐거나 위험하다. |

### 기본값은 물리 삭제가 아니라 비활성화다

[OBO Foundry의 용어 안정성 원칙](https://obofoundry.org/principles/fp-019-term-stability.html)은
폐기된 용어의 식별자와 텍스트 정의를 남기고,
논리 공리를 제거하며,
정확한 대체 대상 또는 검토할 후보와 폐기 이유를 기록하도록 한다.

도메인은 다르지만 운영 원칙은 일반화할 가치가 있다.

```text
status = deprecated
deprecatedAt
deprecatedReason
replacedBy
consider
lastValidVersion
```

비활성화된 항목은 새 데이터에 쓰지 못하게 막되,
옛 데이터와 링크는 이전 가능한 상태로 유지한다.

### 비활성화 후보

다음 조건 중 하나가 강하게 성립하면 검토한다.

- 어떤 역량 질문, 제약, 행동에서도 사용되지 않는다.
- 더 정확한 개념으로 완전히 대체됐다.
- 의미가 겹쳐 지속적으로 개체 해소 오류를 만든다.
- 정의할 수 없을 정도로 모호하다.
- 소유자와 출처가 없고 검증할 방법도 없다.
- 원천에서 더 이상 생성되지 않으며 유지 비용만 발생한다.
- 민감 정보, 비밀, 법적 삭제 대상이다.

사용 빈도가 낮다는 이유만으로 빼서는 안 된다.
저빈도지만 중요한 장애, 보안 결정, 규제 개념은 높은 가치가 있을 수 있다.

### 물리 삭제 후보

물리 삭제는 더 좁게 적용한다.

- 적재 오류로 생성됐고 어느 공개 버전에서도 참조되지 않은 중복
- 비밀이나 개인정보가 잘못 유입돼 보존 자체가 위험한 항목
- 테스트·임시 데이터가 운영 그래프에 들어간 경우
- 법적 또는 계약상 삭제 의무가 있는 경우

삭제 전에는 다음을 확인한다.

- 들어오고 나가는 모든 관계
- 저장된 질의와 응용 프로그램 참조
- 별칭과 외부 매핑
- 캐시와 검색 색인
- 평가 정답
- 원본 보존 정책

### “빼기”는 컨텍스트 조립에서도 수행한다

온톨로지에 남겨야 하지만 매번 모델에게 보여줄 필요가 없는 데이터가 많다.

컨텍스트에서 제외할 대표 항목은 다음과 같다.

- 현재 질문과 관계없는 고차수 이웃
- 동일 근거의 반복 사본
- 오래됐고 더 최신 버전으로 대체된 문서
- 권한이 없는 원문
- 출처가 불명확한 추출 주장
- 토큰을 많이 쓰지만 답변 기여도가 낮은 전체 파일
- 생성 파일, 잠금 파일, 바이너리, 비밀 경로

이 구분이 중요하다.

온톨로지에서의 폐기는 의미 계약의 변경이고,
컨텍스트에서의 제외는 현재 작업을 위한 선택이다.

## 온톨로지 품질을 어떻게 측정할 것인가

한 점수로 합치지 말고 독립된 축을 유지한다.

### 논리·스키마 정합성

- 허용하지 않은 유형과 관계 수
- 모순 또는 만족 불가능한 클래스
- 방향, 정의역, 공역 위반
- 필수 속성 누락
- 폐기된 항목의 활성 사용

### 정확성과 근거

- 표본 관계 정밀도
- 표본 관계 재현율
- 출처 보유율
- 출처 원문과 주장 일치율
- 추출 버전과 변경 이력 보유율

### 개체 품질

- 중복 의심 개체
- 하나의 이름에 여러 의미가 섞인 비율
- 고빈도 개체의 정식 사전 적중률
- 별칭으로 회복되는 질문 비율
- 고아 개체와 고아 문서 비율

### 질문 적합성

- 역량 질문별 경로 존재
- 정답 노드 도달률
- 난이도별 성공률
- 인과·시간·비교 질문 성공률
- 필수 근거 회수율

### 운영 가능성

- 변경 제안의 소유자 보유율
- 변경 영향 분석 가능 여부
- 이전 규칙과 되돌리기 가능 여부
- 새 원천 반영 지연
- 실패한 추출의 재처리 가능 여부

### 사용자 가치

- 사람이 답을 찾는 데 걸리는 시간
- 답변 후 올바른 다음 행동으로 이어지는 비율
- 잘못된 근거 인용률
- 에이전트 작업 성공률
- 필요한 컨텍스트를 찾기 위한 도구 호출 수

[OQuaRE](https://research.manchester.ac.uk/en/publications/oquare-a-square-based-approach-for-evaluating-the-quality-of-onto/)는
소프트웨어 품질 모델을 온톨로지 평가에 적용하는 체계를 제공한다.
다만 최근 품질 연구가 지적하듯 내재 품질만으로 실제 과업 유용성을 충분히 평가하기 어렵다.
따라서 `devloop-v2`처럼 그래프 정적 지표와 질문 기반 외재 평가를 함께 두는 것이 타당하다.

### Google Data Commons

[Data Commons 논문](https://research.google/pubs/data-commons/)은
여러 공개 데이터의 서로 다른 스키마, 형식, 가정을 공통 스키마와 API로 통합하고,
분산된 Data Commons를 하나의 지식그래프처럼 조회하는 구조를 설명한다.

배울 점:

- 통합 가치는 그래프 저장소보다 공통 스키마와 식별자에서 나온다.
- 원천별 차이를 한 번 조정해 여러 소비자가 재사용하게 한다.
- 사람이 RDF를 직접 다루게 하기보다 [REST API](https://docs.datacommons.org/api/rest/v2) 같은 소비 인터페이스를 제공한다.

### Google Knowledge Vault

[Knowledge Vault 논문](https://research.google/pubs/knowledge-vault-a-web-scale-approach-to-probabilistic-knowledge-fusion/)은
텍스트, 표, 페이지 구조, 사람 주석, 기존 지식 저장소에서 추출한 사실을 결합하고
사실 정확성의 보정된 확률을 계산하는 확률적 지식베이스를 제안한다.

배울 점:

- 자동 추출 결과를 이진 사실로 바로 승격하지 않는다.
- 서로 다른 출처와 추출 방법을 융합한다.
- 신뢰도는 모델의 임의 숫자가 아니라 검증된 확률 또는 운영 상태와 연결해야 한다.

### LinkedIn Knowledge Graph와 Skills Graph

[LinkedIn Knowledge Graph 구축 글](https://www.linkedin.com/blog/engineering/knowledge/building-the-linkedin-knowledge-graph)은
회원, 직무, 기술, 회사, 위치, 학교 등의 개체와 관계를 전문 직업 세계의 온톨로지로 사용한다고 설명한다.
사용자 생성 데이터의 노이즈와 중복을 표준화하고,
분류 체계 생성, 관계 추론, 사용자 상호작용을 통한 검증을 결합한다.

그래프는 Java 라이브러리, REST API, Kafka, HDFS 파일 등 온라인·오프라인 소비 방식으로 배포된다.

[Skills Graph 유지관리 글](https://www.linkedin.com/blog/engineering/data/building-maintaining-the-skills-taxonomy-that-powers-linkedins-skills-graph)은
기술 분류 체계를 지속적으로 확장하고 다국어·새 기술·중복을 관리하는 운영 문제를 보여준다.

배울 점:

- 지식그래프는 하나의 조회 제품이 아니라 여러 제품이 같은 언어를 쓰게 하는 데이터 계약이다.
- 실시간 변경과 일괄 배포를 함께 지원한다.
- 사용자 상호작용은 추론을 검증하고 학습 데이터를 얻는 피드백 통로가 될 수 있다.
- 분류 체계 유지관리에는 전담 소유권과 반복 평가가 필요하다.

### Airbnb 여행 지식그래프

[Airbnb의 지식그래프 구조](https://medium.com/airbnb-engineering/contextualizing-airbnb-by-building-knowledge-graph-b7077e268d5a)는
도시, 명소, 행사, 숙소 등 서로 다른 노드 유형과 관계 유형을 정의하고,
각 관계에 출처와 신뢰도를 보존하며,
여러 팀이 각자의 데이터 소유권을 유지한 채 그래프에 기여하는 방식을 설명한다.

특히 당시에는 운영 성숙도가 높은 관계형 저장소 위에 노드·엣지 계층을 만들었다.
이는 지식그래프의 핵심이 반드시 전용 그래프 데이터베이스 선택에 있지 않다는 사례다.

[2026년 Airbnb 통합 그래프 기반 구조](https://medium.com/airbnb-engineering/scaling-airbnbs-identity-graph-with-a-unified-knowledge-graph-infrastructure-ebac467b7836)는
신원 그래프가 70억 노드와 110억 관계, 하루 약 500만 개의 새 관계를 다루며
신뢰·안전 업무의 여러 단계 탐색에 쓰인다고 자기보고한다.

배울 점:

- 관계의 출처와 팀 소유권을 데이터에 포함한다.
- 저장, 질의 API, 변경 수집·배포를 분리한다.
- 저장소 기술은 질의 형태, 운영 역량, 지연 목표에 따라 바뀔 수 있다.
- 큰 그래프에서는 고차수 노드와 긴 꼬리 지연을 별도 문제로 다룬다.

### Uber Eats 음식 지식베이스

[Uber Eats 질의 이해 엔진](https://www.uber.com/en-BE/blog/uber-eats-query-understanding/)은
여러 원천 데이터를 음식 도메인 온톨로지에 맞춰 변환하고,
분류기로 중복 제거와 원천 간 연결을 수행해 검색 의도를 이해한다.

배울 점:

- 온톨로지는 너무 일반적인 데이터 덩어리와 지나치게 경직된 스키마 사이의 균형 장치다.
- 개체 해소는 적재 뒤 청소 작업이 아니라 핵심 파이프라인 단계다.
- 최종 평가는 온톨로지 자체보다 검색 의도 이해와 제품 결과에서 이뤄진다.

### Uber Databook

[Uber Databook](https://www.uber.com/us/en/blog/metadata-insights-databook/)은
데이터 집합, 열, 지표, 대시보드, 파이프라인, 기계학습 특성 같은 내부 데이터 자산을
메타데이터 그래프와 이벤트 로그로 연결한다.

공개 글은 공통 스키마, 이전 버전과의 호환성, 중앙 검토 조직,
API와 사용자 화면을 함께 운영하는 방식을 설명한다.

배울 점:

- 에이전트 컨텍스트에는 문서 내용뿐 아니라 소유자, 생산 파이프라인, 하류 소비자, 최신 변경을 포함해야 한다.
- 메타데이터 변경을 이벤트로 남기면 검색 색인, 구독자, 감사 로그에 일관되게 전파할 수 있다.
- 새로운 자산 종류를 쉽게 추가하려면 중앙 의미 계약과 확장 가능한 등록 절차가 함께 있어야 한다.

### Meta의 데이터 이해와 내부 지식 투영

[Meta의 대규모 데이터 이해 체계](https://engineering.fb.com/2025/04/28/security/how-meta-understands-data-at-scale/)는
대규모 데이터 자산을 공통 프라이버시 분류 체계와 주석으로 해석하고,
정책과 개발 도구가 같은 의미를 사용하게 하는 접근을 설명한다.

[내부 파이프라인 지식을 AI용 컨텍스트 파일로 투영한 사례](https://engineering.fb.com/2026/04/06/developer-tools/how-meta-used-ai-to-map-tribal-knowledge-in-large-scale-data-pipelines/)는
거대한 내부 구조를 에이전트가 매번 탐색하게 하지 않고,
검토 가능한 작은 컨텍스트 파일로 만들고 비평기와 주기적 검증으로 최신성을 유지하는 방식을 설명한다.
글에서 제시한 도구 호출 감소와 탐색 범위 수치는 회사 자기보고다.

배울 점:

- 정식 의미 계층과 에이전트에 넣는 투영물은 같은 것이 아니다.
- 에이전트용 투영은 작고, 검토 가능하고, 다시 생성 가능해야 한다.
- 자동 생성 컨텍스트에는 비평, 누락 검사, 최신성 검사가 필요하다.
- 민감도와 정책 분류는 검색 뒤 필터가 아니라 의미 계약과 수집 단계에 포함하는 편이 안전하다.

### Palantir Foundry Ontology

[Palantir의 온톨로지 시스템 설명](https://www.palantir.com/docs/foundry/architecture-center/ontology-system)은
개체·관계·속성만이 아니라 행동, 함수, 자동화, 권한을 같은 운영 계층에 연결한다고 설명한다.
사람과 AI 에이전트가 같은 실제 세계 상태를 읽고,
권한이 허용하는 행동을 실행하며,
결과를 다시 시스템에 기록하는 폐쇄 고리를 목표로 한다.

[Action Log](https://www.palantir.com/docs/foundry/action-types/action-log)는
변경 행동 자체를 개체로 기록하고,
변경한 모든 개체와 당시 컨텍스트를 연결하는 패턴을 제공한다.

주의:

- 이는 벤더의 제품 문서와 관점이다.
- 제품의 전체 효과를 독립적으로 검증하는 자료는 아니다.
- “온톨로지”를 전통적인 형식 온톨로지보다 넓은 운영 모델 의미로 사용한다.

배울 점:

- 사람과 에이전트의 공유 컨텍스트에 행동과 권한을 포함할 수 있다.
- 읽기 그래프와 쓰기 행동을 분리하되 같은 의미 계약으로 연결한다.
- 결정과 변경 기록을 일급 개체로 만들면 감사와 학습에 유리하다.

### Microsoft GraphRAG

[GraphRAG 논문](https://arxiv.org/abs/2404.16130)과
[공식 구현 문서](https://microsoft.github.io/graphrag/index/overview/)는
문서에서 개체·관계·주장을 추출하고,
그래프 커뮤니티와 계층별 요약을 미리 생성해,
전체 말뭉치의 주제나 패턴을 묻는 전역 질문에 답하는 방식을 설명한다.

배울 점:

- “특정 사실 찾기”와 “전체 경향 요약”은 다른 검색 문제다.
- 그래프는 관계 탐색뿐 아니라 코퍼스의 계층적 요약 색인이 될 수 있다.
- 색인 비용이 크므로 모든 질문에 GraphRAG를 쓰면 안 된다.
- 추출 그래프가 곧 도메인 온톨로지는 아니다.
  자동 생성된 개체 그래프와 사람이 관리하는 의미 계약을 구분해야 한다.

### Amazon BYOKG와 COSMO

[Bring Your Own KG](https://www.amazon.science/code-and-datasets/bring-your-own-kg)는
처음 보는 지식그래프에 대해 에이전트가 스키마와 도구를 사용해 질의를 구성하는 연구 자산이다.
이 사례의 핵심은 모든 그래프를 한 모델에 학습시키기보다,
그래프별 스키마를 실행 시 컨텍스트로 제공하고 상징적 질의 도구와 결합하는 데 있다.

[COSMO](https://www.amazon.science/publications/cosmo-a-large-scale-e-commerce-common-sense-knowledge-generation-and-serving-system-at-amazon)는
전자상거래의 상식 관계를 대규모로 생성하고,
사람 주석과 비평 분류기를 통해 품질을 거른 뒤 제품에 공급하는 구조를 설명한다.

배울 점:

- 에이전트가 그래프를 쓰려면 전체 데이터를 프롬프트에 넣는 것이 아니라 스키마 탐색과 제한된 질의 도구가 필요하다.
- 생성 모델과 검증 모델 또는 결정적 검사기를 분리한다.
- 연구 벤치마크 수치는 특정 데이터와 설정에 종속되므로 제품 일반 성능으로 해석하지 않는다.

## 사람과 AI 에이전트를 위한 컨텍스트 계층

하나의 거대한 저장소보다 목적이 다른 계층을 연결하는 편이 안전하다.

### 지속 규칙

항상 따라야 하는 팀 규칙, 빌드·검증 명령, 보안 경계를 담는다.

예:

- `AGENTS.md`
- `CLAUDE.md`
- 경로별 규칙
- 조직 정책

OpenAI Codex의 [AGENTS.md 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md)는
전역에서 저장소 하위 경로까지 지침을 계층적으로 결합한다.

Anthropic의 [Claude Code 메모리 문서](https://code.claude.com/docs/en/memory)는
사람이 작성한 지속 지침과 에이전트가 자동 생성한 기억을 분리하고,
긴 지침은 경로별 규칙이나 필요할 때 불러오는 기술로 옮기도록 권한다.

핵심 원칙:

- 반드시 지켜야 할 규칙은 자동 기억에만 두지 않는다.
- 모든 작업에 필요하지 않은 절차는 시작 컨텍스트에 넣지 않는다.
- 강제해야 하는 보안 제약은 자연어 지침이 아니라 실행 계층에서도 막는다.

### 의미 계층

도메인 개념, 관계, 식별자, 제약, 변경 이력을 담는다.

예:

- 제품·컴포넌트·업무·결정 온톨로지
- 코드 심볼과 호출·의존 관계
- 조직, 소유권, 서비스 카탈로그
- 문서 유형과 신뢰 등급

이 계층은 검색어를 확장하고,
다른 원천의 같은 개체를 연결하며,
잘못된 관계 탐색을 차단한다.

### 원본 근거 계층

정답을 인용하고 재검증할 수 있는 원본 또는 변경 불가능한 참조를 담는다.

예:

- Git 커밋의 파일 내용
- Dooray 업무와 댓글
- 위키 문서의 특정 버전
- 설계 결정 기록
- 테스트 출력과 장애 로그

의미 계층의 모든 중요한 주장은 이 계층으로 돌아갈 수 있어야 한다.

### 실시간 운영 계층

호출 시점에만 정확한 상태를 제공한다.

예:

- 현재 CI 상태
- 배포 버전
- 장애 현황
- 이슈와 풀 리퀘스트 상태
- 권한과 사용자 역할

이 값은 장기 기억에 복사하기보다 도구로 다시 조회한다.

### 작업 기억

현재 작업의 계획, 이미 읽은 근거, 아직 확인하지 않은 가설, 실패한 시도를 담는다.

작업이 끝난 뒤 다음 중 하나로 정리한다.

- 버린다.
- 검증된 내용만 지속 문서로 승격한다.
- 자동 기억 후보로 남긴다.
- 온톨로지 변경 제안으로 보낸다.

## 코딩 에이전트 컨텍스트 제공 구조

### 저장에서 주입까지의 전체 흐름

```text
원천
  ↓ 수집·버전 고정·권한 표시
정규화
  ↓ 식별자·청크·심볼·개체·출처
다중 색인
  ↓ 키워드·심볼·그래프·벡터·시간
검색 계획
  ↓ 질문 유형·원천 선택·확장 범위
후보 회수
  ↓ 권한·최신성·정밀도 필터
컨텍스트 조립
  ↓ 중복 제거·순위화·토큰 예산·인용
에이전트 주입
  ↓ 지침·자원·도구 결과
실행과 답변
  ↓ 사용 근거·도구 호출·결과 기록
평가와 환류
```

### 하나의 검색 방식으로 통일하지 않는다

코드 작업은 서로 다른 검색이 필요하다.

- 정확한 문자열과 오류 메시지: 키워드 검색
- 정의, 참조, 구현체: 언어 서버 또는 코드 인텔리전스
- 파일과 심볼의 의존 관계: 코드 그래프
- 자연어와 코드의 의미 유사성: 벡터 검색
- 결정의 배경과 시간 순서: 지식그래프
- 최신 실행 상태: 도구 호출

[Sourcegraph Cody 컨텍스트 문서](https://sourcegraph.com/docs/cody/core-concepts/context)는
키워드 검색, Sourcegraph 검색, 코드 그래프를 함께 사용한다.
또한 [컨텍스트 필터](https://sourcegraph.com/docs/cody/capabilities/ignore-context)로
에이전트가 외부 모델에 보낼 수 있는 저장소를 제한한다.

[Continue 컨텍스트 제공자 문서](https://docs.continue.dev/customize/custom-providers)는
파일, 심볼, 변경 diff, 터미널, 문서, 코드베이스, 검색, 저장소 지도, MCP 등 서로 다른 공급원을 명시적인 제공자로 노출한다.

### 구조 검색은 벡터 검색을 보완한다

[RepoCoder](https://arxiv.org/abs/2303.12570)는
저장소 수준 코드 완성에서 검색과 생성을 반복해 단순한 파일 내부 또는 한 번의 검색보다 나은 결과를 보고했다.

[CatCoder](https://arxiv.org/abs/2406.03283)는
정적 분석으로 얻은 유형 의존성을 검색 결과와 결합해,
단순 유사도 검색이 놓치는 더 넓고 깊은 저장소 컨텍스트를 보완한다.

이 연구들의 실무적 의미는 “벡터 검색이 필요 없다”가 아니다.
코드는 텍스트인 동시에 심볼·유형·호출·테스트로 연결된 구조라는 것이다.

코드 구조 계층의 대표 표준과 구현은 다음과 같다.

- [LSP 3.17](https://github.com/Microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/specification.md):
  편집기와 언어 서버 사이에서 정의, 참조, 진단, 완성 같은 기능을 교환한다.
- [SCIP](https://github.com/sourcegraph/scip/):
  저장소를 미리 색인해 여러 도구가 정확한 코드 탐색 정보를 재사용하게 한다.
- [Sourcegraph 정밀 코드 탐색](https://sourcegraph.com/docs/code-navigation/precise-code-navigation):
  SCIP 색인과 검색 기반 대체 경로를 결합한다.

의미 지식그래프가 이 계층을 대체하려 해서는 안 된다.
코드의 정의·참조는 언어 도구가 더 정확하게 알고,
지식그래프는 코드 심볼을 업무, 결정, 소유자, 문서, 장애와 연결하는 역할을 맡는 편이 좋다.

### 저장소 지도는 전체 코드를 작게 투영한다

[Aider 저장소 지도](https://aider.chat/docs/repomap.html)는
파일 전체를 보내는 대신 주요 클래스·함수·서명과 관계를 추출하고,
그래프 순위를 사용해 토큰 예산 안에서 중요한 심볼을 선택한다.

이 패턴은 `devloop-v2`에도 잘 맞는다.

- 온톨로지 전체: 장기 의미 계약
- 저장소 지도: 현재 커밋의 코드 구조 투영
- 질문별 근거 묶음: 현재 작업 컨텍스트

세 계층을 분리하면 코드가 바뀔 때 온톨로지를 매번 다시 만들 필요가 없고,
에이전트에 전체 그래프를 넣을 필요도 없다.

### 사람이 큐레이션한 컨텍스트 공간도 유용하다

[GitHub Copilot Spaces](https://docs.github.com/en/copilot/concepts/context/spaces)는
저장소, 파일, 이슈, 풀 리퀘스트, 메모 등을 특정 주제의 공유 컨텍스트로 묶는다.

이는 자동 검색과 다른 문제를 해결한다.

- 팀이 어떤 자료를 권위 있는 출발점으로 보는지 명시한다.
- 신규 구성원과 에이전트가 같은 묶음에서 시작한다.
- 특정 프로젝트나 사고 대응처럼 수명이 있는 컨텍스트를 관리한다.

다만 큐레이션 공간도 원본을 복사해 고정하면 오래될 수 있다.
가능하면 원본 링크와 버전을 보존하고 자동 최신성 검사를 둔다.

### 장기 메모리는 계층과 승격 규칙이 필요하다

[MemGPT](https://arxiv.org/abs/2310.08560)는
제한된 컨텍스트 창을 운영체제의 메모리 계층처럼 관리하는 가상 컨텍스트 접근을 제안한다.

[Letta의 메모리 블록](https://docs.letta.com/guides/core-concepts/memory/memory-blocks)은
항상 보이는 작은 메모리 블록과 필요할 때 접근하는 외부 저장소를 분리하는 제품화된 예다.

실무에서 더 중요한 것은 저장 방식보다 승격 규칙이다.

```text
대화 관찰
  → 반복 확인
  → 원본 근거 검증
  → 사람 승인 또는 자동 검사
  → 지속 지침 / 온톨로지 / 운영 문서 중 적절한 위치로 승격
```

자동 기억에만 남은 항목은 도움이 되는 회상 후보이지 조직의 확정 사실이 아니다.

### 긴 컨텍스트는 검색 실패를 해결하지 않는다

[Lost in the Middle](https://arxiv.org/abs/2307.03172)은
관련 정보의 위치에 따라 긴 입력 사용 성능이 크게 달라지고,
중간에 있는 정보를 잘 활용하지 못하는 현상을 보고했다.

따라서 컨텍스트 창이 커져도 다음은 필요하다.

- 관련 후보를 먼저 좁힌다.
- 가장 중요한 지침과 근거를 분명한 위치에 둔다.
- 중복과 저가치 파일을 제거한다.
- 인용 가능한 작은 근거 묶음을 만든다.
- 검색 결과가 부족하면 에이전트가 추가 호출할 수 있게 한다.

### MCP의 역할을 정확히 제한한다

[MCP 공식 구조](https://modelcontextprotocol.io/docs/learn/architecture)는
호스트, 클라이언트, 서버 구조에서 다음 세 가지 핵심 원시 기능을 정의한다.

- 자원: 읽을 컨텍스트 데이터
- 도구: 실행 가능한 함수
- 프롬프트: 재사용 가능한 상호작용 틀

MCP는 컨텍스트 교환 규약이다.
어떤 정보를 검색할지, 무엇을 토큰 예산에 넣을지, 어떤 결과를 신뢰할지는 호스트와 응용 설계의 책임이다.

OpenAI Codex의 [MCP 문서](https://learn.chatgpt.com/docs/extend/mcp.md)는
서버별 도구 허용 목록, 거부 목록, 승인 방식, 인증, 프로젝트별 설정을 제공한다.

따라서 MCP 서버를 만든 것만으로 컨텍스트 품질 문제가 해결되지는 않는다.
서버 내부에 좋은 검색·권한·최신성·출처 계약이 있어야 한다.

### 제공자 응답 계약

에이전트에 반환하는 각 컨텍스트 항목은 가능한 한 다음 필드를 가진다.

```ts
interface ContextItem {
  id: string;
  kind: "source" | "entity" | "claim" | "code" | "instruction" | "state";
  title: string;
  uri: string;
  content: string;
  sourceSystem: string;
  sourceRevision?: string;
  contentHash?: string;
  observedAt?: string;
  validFrom?: string;
  validTo?: string;
  authority: "primary" | "derived" | "inferred";
  status: "active" | "candidate" | "deprecated" | "conflicted";
  sensitivity?: string;
  permissions?: string[];
  score?: number;
  scoreReasons?: string[];
  relationPath?: string[];
  citations: Array<{ uri: string; locator?: string }>;
  tokenEstimate: number;
}
```

모든 시스템이 이 형식을 그대로 쓸 필요는 없다.
그러나 출처, 버전, 상태, 권한, 점수 이유, 토큰 크기는 운영 중 반드시 필요해진다.

### 제공자 도구의 최소 집합

읽기 전용 첫 버전은 다음으로 충분하다.

```text
search(query, filters)
get(id)
expand(id, relationTypes, depth)
getEvidence(claimOrEntityId)
getDecisionTrace(entityId, timeRange)
getChangeImpact(ontologyElementId)
```

작은 응답을 기본으로 하고,
에이전트가 필요할 때 확장하게 한다.

### 검색 결과를 조립하는 기준

순위는 유사도 하나가 아니라 다음을 함께 본다.

- 질문과의 관련성
- 원천 권위
- 최신성
- 개체와 관계 경로의 적합성
- 근거 다양성
- 중복 여부
- 권한
- 토큰 비용
- 과거 평가에서의 기여도

간단한 점수식 예시는 다음과 같다.

```text
utility =
  relevance
  × authority
  × freshness
  × permission
  × evidenceQuality
  − redundancyPenalty
  − tokenCostPenalty
```

곱셈 항목 중 권한은 0 또는 1의 강제 필터로 처리하는 편이 안전하다.

### 주입 이후를 추적한다

다음 로그가 없으면 제공자를 개선하기 어렵다.

- 어떤 질문이 들어왔는가?
- 어떤 검색 계획을 선택했는가?
- 어떤 후보를 회수하고 무엇을 버렸는가?
- 모델에 실제로 넣은 항목은 무엇인가?
- 어떤 인용을 답에 사용했는가?
- 도구 호출과 최종 작업 결과는 어땠는가?
- 같은 질문을 반복했을 때 결과가 얼마나 흔들렸는가?

컨텍스트 제공자의 평가는 검색 정확도뿐 아니라 최종 작업 성공률로 끝나야 한다.

### 권한은 검색 전후와 실행 시점에 모두 적용한다

컨텍스트 보안은 모델에 “비밀을 읽지 말라”고 쓰는 문제로 끝나지 않는다.

- 수집 단계에서 색인 가능한 원천을 제한한다.
- 검색 단계에서 사용자와 에이전트의 읽기 권한을 적용한다.
- 조립 단계에서 외부 모델로 보낼 수 없는 항목을 제거한다.
- 도구 단계에서 읽기와 쓰기 권한을 분리한다.
- 행동 단계에서 중요한 변경은 별도 승인과 감사 로그를 요구한다.

[Sourcegraph 컨텍스트 필터](https://sourcegraph.com/docs/cody/capabilities/ignore-context)는
검색 컨텍스트로 사용할 수 있는 저장소를 관리자 정책으로 제한하는 사례다.

[GitHub 사용자 정의 에이전트](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-custom-agents)는
에이전트 프로필에 사용할 도구와 MCP 서버를 명시한다.

OpenAI Codex의 [MCP 설정](https://learn.chatgpt.com/docs/extend/mcp.md)은
서버와 도구별 허용 목록, 거부 목록, 승인 방식을 제공한다.

온톨로지는 권한을 설명할 수 있지만,
실제 차단은 검색기, 컨텍스트 제공자, 도구 실행 계층이 수행해야 한다.

## 컨텍스트 제공 방식 비교

| 방식 | 강점 | 약점 | 적합한 내용 |
| --- | --- | --- | --- |
| 시작 지침 파일 | 항상 보이는 규칙과 저장소 관례 | 길어질수록 토큰과 준수율 저하 | 빌드 명령, 금지 사항, 검증 규칙 |
| 경로별 지침 | 관련 코드에만 세부 규칙 적용 | 도구별 탐색 규칙 차이 | 서비스별 관례, 언어별 규칙 |
| 기술 | 필요할 때만 절차 로드 | 활성화 조건과 유지보수 필요 | 반복 가능한 검토·배포·분석 절차 |
| 키워드 검색 | 빠르고 정확한 문자열 회수 | 의미가 다른 표현을 놓침 | 오류, 심볼, 설정 키 |
| 언어 서버·코드 인덱스 | 정의·참조·유형 관계에 강함 | 언어별 색인 필요 | 심볼 탐색, 영향 범위 |
| 벡터 검색 | 표현이 다른 의미 유사 문서 회수 | 최신성·권한·정확한 식별에 약함 | 문서·코드 후보 넓히기 |
| 지식그래프 | 다단계 관계, 출처, 시간, 개체 해소 | 구축·변경 관리 비용 | 결정 이력, 소유권, 의존성 |
| MCP 자원 | 표준 방식의 읽기 컨텍스트 제공 | 선택·순위 품질은 별도 문제 | 문서, 개체, 스키마 |
| MCP 도구 | 실시간 조회와 제한된 행동 | 권한·승인·부작용 설계 필요 | CI, 이슈, 데이터베이스, 배포 상태 |
| 자동 기억 | 반복 학습을 낮은 비용으로 보존 | 부정확·오래된 관찰이 축적될 수 있음 | 개인 선호, 반복 디버깅 단서 |

핵심은 하나를 선택하는 것이 아니라 각 내용을 가장 작은 적절한 계층에 두는 것이다.

## `devloop-v2`에 대한 진단

### 이미 잘하고 있는 점

#### 온톨로지가 코드 계약이다

[온톨로지 상수](../../packages/shared/src/ontology/ontology.const.ts)와
[온톨로지 Zod 스키마](../../packages/shared/src/ontology/ontology.schema.ts)에서
라벨, 키, 속성, 관계 방향을 TypeScript와 Zod로 관리한다.
문서와 코드가 완전히 분리된 그림이 아니라 실행 시 검증 가능한 계약이다.

#### 구조 추출과 LLM 추출을 구분한다

작성자, 담당자, 댓글, 명시 참조 같은 구조 정보는 규칙으로 추출하고,
개념·의존·의사결정·인과 후보만 LLM에 맡긴다.
이 분리는 [구조 추출기](../../apps/pipeline/src/extract/structural-extractor.ts)와
[LLM 추출 프롬프트](../../apps/pipeline/src/extract/extraction-prompt.ts)에서 직접 확인할 수 있다.

이는 비용뿐 아니라 검증 가능성을 높인다.

#### 출처를 필수로 둔다

LLM 생성 노드와 관계에 `sourceDocId`를 요구한다.
[추출 프롬프트](../../apps/pipeline/src/extract/extraction-prompt.ts)와
[LLM 출력 스키마](../../apps/pipeline/src/extract/llm-extraction.schema.ts)가 이를 강제한다.
출처 없는 추론을 적재 단계에서 거부할 기반이 있다.

#### 실제 질문으로 외재 평가한다

[평가 기준](../EVAL-RUBRIC.md)은 사람 질문과 AI 질문,
단순 조회부터 비교·인과까지의 난이도,
정적 그래프 품질과 답변 품질을 분리한다.

이는 전통적인 역량 질문을 실제 검색·답변 평가로 확장한 구조다.

#### 개체 파편화와 평가 오류까지 측정한다

현재 저장소의
[개념 별칭 후보 리포트](../../eval/reports/2026-07-28-concept-alias-candidates.md),
[근거 도달성 리포트](../../eval/reports/2026-07-28-gold-reachability.md),
[앵커 반복 측정 리포트](../../eval/reports/2026-07-28-anchor-resolution.md)는
다음을 이미 발견했다.

- 전체 `Concept`의 일부 고빈도 항목이 대부분의 참조를 덮는다.
- 문자열 포함과 토큰 일치가 잘못된 병합을 만들 수 있다.
- 일부 평가 정답은 원천 데이터에 근거가 없다.
- 한 번의 통과는 비결정적 LLM 질의의 안정성을 증명하지 못한다.
- 실패가 문항보다 특정 노드의 도달 실패에 집중된다.

이것은 온톨로지 진화를 감으로 하지 않고 관찰 가능한 실패에서 시작할 수 있게 한다.

### 현재 가장 큰 공백

이 절은 위 코드와 평가 리포트를 연결해 내린 필자의 종합 판단이다.

#### `Concept`가 어휘와 개체 역할을 함께 맡는다

[온톨로지 정의](../../packages/shared/src/ontology/ontology.const.ts)와
[추출 프롬프트](../../apps/pipeline/src/extract/extraction-prompt.ts)의 `Concept(name, kind)`는
다음을 함께 담는다.

- 태그 분류 항목
- 제품과 컴포넌트
- 기술
- 코드 참조
- 본문에서 추출한 일반 개념

이들은 식별 기준, 생명주기, 병합 규칙이 다르다.

당장 클래스를 많이 추가하기보다 후보 상태와 식별 근거부터 분리한다.

예:

```text
conceptId
canonicalName
kind
definition
status
owner
identityBasis
createdFrom
replacedBy
```

#### 별칭은 존재하지만 변경 생명주기가 없다

[개념 사전](../../packages/shared/src/concept/concept.const.ts),
[사전 시드](../../apps/pipeline/src/extract/concept-seeder.ts),
[적재 정규화](../../apps/pipeline/src/load/load.ts)는 실용적이지만
현재 계약만으로는 다음을 표현하기 어렵다.

- 누가 왜 별칭을 승인했는가?
- 공식 개명인가, 단순 줄임말인가?
- 어느 기간에 유효했는가?
- 잘못 승인된 별칭을 어떻게 되돌리는가?
- 병합 때문에 어떤 질문의 경로가 바뀌는가?

별칭 변경도 온톨로지 변경 제안으로 관리하고,
승인 근거와 영향 평가를 남긴다.

#### 관계가 주장인지 사실인지 상태가 약하다

현재 [관계 정의](../../packages/shared/src/ontology/ontology.const.ts)의
`DEPENDS_ON`, `RELATES_TO`, `AFFECTS`는 해석이 개입될 수 있지만
현재는 출처 외에 추출 방식, 검토 상태, 시간 유효성, 신뢰 이유가 충분히 드러나지 않는다.

관계 속성을 보강하거나 중요한 관계를 `Claim`으로 승격한다.

#### 변경 영향 검사 계약이 없다

[온톨로지 상수](../../packages/shared/src/ontology/ontology.const.ts)가
[추출 프롬프트](../../apps/pipeline/src/extract/extraction-prompt.ts),
[Neo4j 스키마](../../apps/pipeline/src/load/schema.cy),
[질의 서비스](../../apps/api/src/query/query.service.ts),
[프론트엔드 온톨로지 화면](../../apps/web/src/OntologyPage.tsx),
[평가 기준](../EVAL-RUBRIC.md)에 걸쳐 사용되므로,
변경 영향을 자동으로 보여주는 계약이 필요하다는 것이 필자의 판단이다.

- 추출 프롬프트
- Zod 스키마
- Neo4j 제약
- 저장된 그래프
- 질의 프롬프트
- UI 범례와 탐색
- 평가 질문과 정답

#### 에이전트 소비 인터페이스가 답변 API에 묶여 있다

현재 [`/api/query` 컨트롤러](../../apps/api/src/query/query.controller.ts)와
[질의 서비스](../../apps/api/src/query/query.service.ts)는
사람의 자연어 질문과 최종 답변을 한 흐름에서 처리한다.
코딩 에이전트는 더 작은 구조화 응답이 필요하다.

예:

- 특정 개체의 식별자만 찾기
- 결정 근거 경로만 받기
- 원문 일부와 위치 받기
- 현재 개념의 별칭·폐기 상태 확인
- 온톨로지 변경의 영향 확인

이 기능은 최종 답변 생성과 분리한 읽기 도구로 제공하는 편이 낫다.

## 권장 목표 구조

### 의미 계약

저장소에서 검토 가능한 선언 파일을 단일 원천으로 둔다.

```text
ontology/
├── types
├── relationships
├── constraints
├── concepts
├── aliases
├── changes
└── competency-questions
```

현재 TypeScript 상수를 유지해도 된다.
중요한 것은 각 항목이 정의, 상태, 소유자, 출처, 변경 이력을 가지는 것이다.

### 주장과 근거

```text
Source ──contains──> EvidenceSpan
Claim ──supportedBy──> EvidenceSpan
Claim ──asserts──> Subject / Predicate / Object
Claim ──generatedBy──> ExtractorRun
Claim ──reviewedBy──> Review
Claim ──supersededBy──> Claim
```

모든 관계를 이 구조로 바꿀 필요는 없다.
구조적 관계는 현재처럼 직접 저장하고,
충돌·시간·검토가 중요한 LLM 추출 관계부터 적용한다.

### 사람용 소비

- 온톨로지 지도
- 개념 상세와 정의
- 별칭과 병합·분리 이력
- 근거 원문
- 관련 질문과 통과 여부
- 변경 영향 미리보기
- 후보 승인 대기열

### 에이전트용 소비

- 안정적인 ID
- 작은 JSON 응답
- 원문 위치와 인용
- 활성·후보·폐기 상태
- 권한과 민감도
- 시간 범위
- 관계 경로
- 추가 확장용 커서 또는 도구

- 권한 경계가 흐려짐

대응:

- 작은 기본 컨텍스트와 필요할 때 확장하는 도구를 사용한다.

결과:

- 생성 과정과 승인자가 불명확하다.
- 오래된 관찰이 남는다.
- 사람과 다른 에이전트가 검토하기 어렵다.

대응:

- 승인된 지식은 저장소 문서나 온톨로지에 승격한다.
- 자동 기억은 회상 후보로만 취급한다.

### 평가 질문이 원천보다 옳다고 가정한다

결과:

- 존재하지 않는 관계를 만들도록 추출기를 압박한다.
- 환각을 개선으로 오인한다.

대응:

- 정답 노드 존재, 경로 존재, 원천 존재를 순서대로 검증한다.
- `devloop-v2`의 도달성 검사처럼 평가 자료 자체도 감사한다.

---

## 최종 제안

`devloop-v2`의 다음 학습 목표를 “온톨로지 자동 진화”로 바로 잡지 않는 편이 좋다.

더 좋은 순서는 다음과 같다.

1. 현재 질문 은행을 온톨로지 역량 질문으로 정식 연결한다.
2. 개념·관계 후보에 상태, 출처, 소유자, 변경 이유를 부여한다.
3. 병합·분리·비활성화를 회귀 평가가 있는 변경 절차로 만든다.
4. 최종 답변 API와 별도로 작은 근거 묶음을 반환하는 컨텍스트 제공자를 만든다.
5. 사람과 코딩 에이전트가 같은 의미·근거 계층을 다른 인터페이스로 소비하게 한다.
6. 검색 품질이 아니라 실제 작업 성공률로 환류한다.

이 과정을 거치면 온톨로지는 정적인 그림이 아니라
질문, 근거, 변경, 행동을 연결하는 살아 있는 운영 계약이 된다.

## 근거 해석상의 한계

- W3C 문서는 표준 언어와 의미를 설명하지만 특정 조직의 운영 성공을 보장하지 않는다.
- 기업 기술 글은 실제 구조를 배울 수 있는 강한 1차 자료지만 선택적 자기보고다.
- 제품 문서는 현재 기능을 설명하지만 효과 비교 실험은 아니다.
- arXiv 논문 중 일부는 동료 심사가 완료되지 않았을 수 있다.
- GraphRAG, 에이전트 메모리, 저장소 수준 코드 검색은 빠르게 변하는 분야다.
- `devloop-v2` 적용 제안은 현재 저장소 코드와 평가 리포트를 바탕으로 한 종합 판단이며, 외부 자료가 직접 검증한 결과가 아니다.
