# 원천 형태로 스펙을 써서 규칙이 0건 매칭됐다

## 관찰

Phase 01 은 GitHub 훅 댓글 머리말을 "두 줄 고정 형태" 로 규정했고 구현도 줄 단위로 했다.
첫 줄을 훅으로 판정하고 이어지는 링크 전용 줄을 벗기는 방식이다. 단위 테스트가 전부 통과했다.

그런데 실제 데이터로 `parse-structure` 를 돌리니 Comment 854건 중 **훅 359건 전부**의 `excerpt` 가
여전히 `[[` 로 시작했다. Phase 01 자체 검증 항목을 만족하지 못하는 상태였다.

## 원인

`addCommentNode` 에 도착하는 문자열에는 개행이 없다.
호출부가 넘기는 값이 `textContent`(`raw-reader.ts`)를 거치고, 그 함수가 `\s+` 를 공백 하나로
병합하기 때문이다. 원천 JSON 은 두 줄이지만 저장 직전 함수가 받는 값은 한 줄이다.

줄 단위 규칙은 원리적으로 매칭될 수 없었다. 스펙을 **원천 형태**로 검증하고 적었고,
테스트 픽스처도 같은 원천 형태로 만들었기 때문에 테스트는 통과하는데 실제 데이터는 실패했다.

## 영향

테스트가 전부 초록인데 기능이 하나도 동작하지 않았다.
단위 테스트와 실제 데이터 확인을 둘 다 하라는 절차가 없었다면 그대로 커밋됐을 상태다.

같은 뿌리에서 두 번째 결함도 나왔다 — 훅 판정 정규식을 `pushes?` 로 썼다.
그것은 `pushe` 뒤의 `s` 가 선택이라는 뜻이라 정작 `push` 를 놓친다.
실측 훅 359건 중 3건이 단수형이라 그 3건이 미처리로 남았다.

## 대응

저장용 텍스트만 개행을 보존하는 추출(`textContentPreservingLineBreaks`)을 `raw-reader.ts` 에 더했다.
참조 추출은 기존 `textContent` 값을 그대로 받게 두어 `REFERENCES` 328건을 불변으로 유지했다.

개행을 보존한 이유는 판정 때문만이 아니다. 6,000자를 담으면 마크다운 표·목록·헤딩이 뭉개지고,
표의 행 경계가 사라지면 값을 다른 행에서 잘못 읽어 답이 틀릴 수 있다.
실측 정답 댓글의 조치 내용이 표다.

정규식은 `push(?:es)?` 로 고쳤다.

## 검증

- 훅 359건 전부 머리말이 제거되고 `[[` 로 시작하는 `excerpt` 가 0건이다
- 사람 댓글 495건 중 내용이 바뀐 것이 **0건**이다
- `REFERENCES` 328건·`Comment` 854건·자기참조 0건이 불변이다
- 마크다운 표를 담은 `excerpt` 31건이 행 단위로 보존된다
- 변이 검증 — 훅 판정을 무력화하면 사람 댓글 보존 테스트가 실패한다 (원복 확인)
- 단수형 3건을 실제 원천 형태 픽스처로 회귀 고정했다

## 배운 점

**텍스트 규칙은 원천 형태가 아니라 그 규칙을 적용하는 함수에 실제로 도착하는 값을 기준으로 정한다.**
중간 변환 함수가 하나라도 끼면 두 형태가 다르다.

단위 테스트만으로는 이 결함이 드러나지 않는다. 픽스처를 스펙과 같은 형태로 만들면
테스트가 스펙의 오해를 그대로 복제한다. **실제 데이터로 한 번 돌려 산출물을 세는 절차가 그 오해를 깬다.**

## 후속

일반 규칙으로 승격한다. `CLAUDE.md` 의 "텍스트 규칙은 도착하는 값을 기준으로 정한다" 절이 소유한다.
정규식 단수·복수 함정(`push(?:es)?` 대 `pushes?`)도 같은 절에 남겼다.
