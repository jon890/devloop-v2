# kg-model-bench — 모델별 품질·비용 벤치마크

같은 데이터·같은 질문에 대해 모델만 바꿔 실행하고,
"품질이 충분한 것 중 가장 싼(빠른) 모델"을 추출용·질의용 각각 판정한다.

## 비교 축

- **추출 모델**: WP2 LLM 추출(MENTIONS·Decision·RELATES_TO 등)에 쓰는 모델.
- **질의 모델**: /api/query 2단계(anchor 용어 추출, Cypher 생성, 답변 합성)에 쓰는 모델.
- 후보는 CLI 어댑터가 지원하는 것만: `codex exec -m <model>` 의 모델들, `claude -p --model <opus|sonnet|haiku>`.
  실행 전 각 CLI 의 현재 지원 모델을 `--help` 로 확인하고 후보 표를 만든다.

## 전제

- Phase 2 파일럿 세트(30건)와 tc-ocr 질문 은행이 준비돼 있어야 한다.
- 추출 캐시는 모델별로 분리된다 (`data/cache/<model>/<docId>.json`) — 모델 간 캐시 오염 금지.
- 모델별 적재는 그래프를 분리한다 (Neo4j database 분리 또는 `Project.benchTag` property) — 비교 대상이 섞이면 벤치마크 무효.

## 절차

1. **추출 벤치**: 후보 모델별로 파일럿 30건 추출을 실행하고 측정한다.
    - 측정: 전체 처리 시간, 호출 수, 실패·재시도 횟수, rate limit 도달 횟수, (CLI 가 노출하면) 토큰 사용량.
    - 품질: 모델별 그래프에 정적 기준(S2·S3·S5·S6)과 kg-eval-human·kg-eval-ai 를 실행해 세트 점수 기록.
2. **질의 벤치**: 추출 그래프는 고정(1에서 가장 좋은 것)하고, 질의 모델만 바꿔 질문 은행을 재실행한다.
    - 측정: 질문당 응답 시간, Cypher 재생성 횟수, 세트 점수.
3. **비용 산정** — 구독 CLI 라 달러 청구는 없다. 비용은 3개 proxy 로 적는다:
    - 전체 처리 시간 (주 지표 — rate limit 이 시간으로 나타난다)
    - 호출 수 × 평균 토큰으로 계산한 API 환산가 (참고용, 공시 단가 기준)
    - rate limit 도달 횟수 (요금제 한도 소모의 직접 신호)
4. **판정 규칙** (기계적으로 적용):
    - 환각 fail 이 1건이라도 있는 모델은 후보에서 탈락.
    - 세트 점수 차이가 5%p 이내면 더 빠른(싼) 모델을 선택.
    - 5%p 초과면 품질 우선 — 단, 처리 시간이 2배 이상이면 사용자에게 트레이드오프를 보고하고 결정을 받는다.
5. **리포트**: `eval/reports/model-bench-<YYYY-MM-DD>.md`
    - 표: 모델 | 역할(추출/질의) | 품질 점수 | 처리 시간 | 호출·재시도 | 환산가 | 판정.
    - 결론: 추출용 권장 모델, 질의용 권장 모델 (둘은 달라도 된다 — 추출은 대량·단순, 질의는 소량·정밀).

## 주의

- 벤치 중 프롬프트·사전을 고치지 않는다 — 모델 외 변인이 섞이면 비교가 무효다.
  개선은 벤치 종료 후 개선 루프에서 한다.
- 판정 결과는 `.env` 의 `LLM_PROVIDER`·모델 설정 기본값에 반영하고 리포트에 링크를 남긴다.
