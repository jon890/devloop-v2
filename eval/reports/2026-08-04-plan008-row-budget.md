# Plan008 다수 업무 조회 측정 리포트

Cypher 가 여러 업무를 확장할 때 `OPTIONAL MATCH` 를 이어 붙이지 말고 `collect()` 로 접어
**업무당 한 행**을 만들게 한 변경의 효과를 측정한다.

- **실제 측정한 문항 수: 12/12**, 두 측정 모두 36/36 attempts, 오류 0건
- 원시 실행 결과는 `eval/runs/` 에 있고 gitignore 대상이라 커밋하지 않는다

## 원인이 `LIMIT` 값이 아니라 쿼리 형태였다

plan007 이후 남은 회수 실패를 진단할 때 `LIMIT 50` 을 의심했으나 **아니었다.**
생성된 Cypher 는 7개 업무를 **모두 지목하고 있었다.**

```cypher
MATCH (t:Task) WHERE t.number IN [483, 494, 496, 497, 498, 499, 506]
OPTIONAL MATCH (p:Project)-[contains:CONTAINS]->(t)
OPTIONAL MATCH (t)-[hasComment:HAS_COMMENT]->(comment:Comment)
OPTIONAL MATCH (t)-[tagged:TAGGED]->(concept:Concept)
OPTIONAL MATCH (d:Decision)-[decided:DECIDED_IN]->(t)
OPTIONAL MATCH (d)-[evidenced:EVIDENCED_BY]->(evidence)
OPTIONAL MATCH (t)-[flowRel:REFERENCES|RELATES_TO|CHILD_OF]-(related:Task)
RETURN ... LIMIT 50
```

`OPTIONAL MATCH` 6개가 곱으로 퍼져 한 업무의 조합이 50행을 독점하고, 다른 업무 노드가
아예 반환되지 않았다. 반환된 업무는 5~7개였다.

**상한을 올리는 것으로 풀 문제가 아니다.** 확장마다 `collect()` 로 접으면 업무당 한 행이 되어
`LIMIT` 이 업무 수만 제한한다. 운영 그래프에 그 패턴을 직접 실행해(읽기 전용) 7개 업무가
모두 반환되는 것을 먼저 확인한 뒤 프롬프트에 넣었다.

`collect` 결과가 근거로 인정되는 것도 확인했다 — `collectEvidence`(`neo4j.service.ts`)가
배열과 객체를 재귀로 훑어 안의 node 를 추출한다.

## 대가 — 지연이 50% 늘었다

| 측정 | 평균 | 기준선 대비 |
| --- | ---: | ---: |
| plan006 기준선 | 48.6초 | — |
| plan007 (두 측정) | 44.4~46.5초 | -5% |
| **plan008 (두 측정)** | **70.2~77.8초** | **+44~60%** |

이번 변경이 지불한 값이다. 업무당 근거가 온전히 담기므로 답변 합성 프롬프트가 커진다.

**회수 실패 10건 감소와 지연 25초 증가의 교환이다.** 이 저장소가 학습 목적의 로컬 도구이고
관리 지표를 비용이 아니라 시간으로 두기로 한 결정(ADR 0002)에 비추면 받아들일 만하다.
대화형 사용을 목표로 하면 다시 볼 항목이다.

## `ANSWER` 경계가 2에서 3으로 늘었다

결정적 순서 검사 실패다. 근거가 늘어 답변이 담을 내용이 많아지면서 사건 순서를 어긋나게 쓰는
회차가 하나 늘었다. 두 측정 모두 3이다.

회수를 10건 줄이고 순서 실패를 1건 늘린 교환이므로 순손실은 아니다. 다만 **다음 개선의
후보로 기록한다** — 근거가 많아질수록 순서 서술이 어려워지는 경향이 실측으로 보인다.

## 의미 판정 범위

두 판정자 의미 판정을 **하지 않았다.** 목표 지표가 결정적 축이고, plan006 에서 36회 중 22회가
채점자 불일치로 `REVIEW` 였던 실측이 있어 정보량이 낮다.

따라서 이 리포트는 **결정적 축만** 근거로 삼는다. 답변 품질의 변화는 판정하지 않았다.

## 측정 절차에서 겪은 것

첫 측정이 **36회 중 35회 `fetch failed`** 로 날아갔다. API 를 측정과 같은 백그라운드 명령 안에서
`pnpm api` 로 띄운 것이 원인이다. `pnpm` 이 자식 출력을 파이프로 중계하므로 그 셸이 끝나면
API 가 다음 로그 쓰기에서 `EPIPE` 로 죽는다. **Nest 는 정상 기동했으므로 기동 실패로 보이지 않았다.**

`node dist/main.js` 를 직접 띄우고 기동·측정을 나눈 호출로 바꿔 재실행했다.
절차는 `docs/pitfalls/measurement.md` 가 소유한다.
