### 실패 내용 — `order` 체크만 실패한다 (그래프 정합은 통과했다)

`deterministicChecks` 를 열어 확인했다. 6개 attempt(두 회차 × 3회) 전부 같은 패턴이다.

- `graph.status`: **PASS** — `task-483`·`task-496` 등 앵커의 노드·관계는 전부 재현된다.
  `missingNodes`·`missingRelationships` 둘 다 비어 있다
- `retrieval.status`: **PASS** — 필수 근거 전부 인용됐다
- `order.status`: **FAIL** — 실패 원인이자 `failedAxes: ["G"]` 로 매핑되는 근거

`failedAxes: ["G"]` 만 보면 그래프 정합 실패로 읽히지만, 실제로 실패한 것은 순서 검사(`order`)이고
그것이 G 축으로 매핑돼 있을 뿐이다. **그래프 정합 자체는 세 축 다 통과했다.**

`AGW-A01` 의 질문은 "Task 496·497·498·499 가 Task 483 의 Phase B 하위 업무라는 근거를 찾고, 답변에는
496 → 497 → 498 → 499 순서로 각 업무의 목적과 검증 순서를 써라"이다. `order` 체크는 답변 텍스트에서
각 번호가 **처음 등장하는 위치**를 찾아 그 순서를 비교한다.

2회차 attempt 1의 실제 답변 서두다.

```
근거: Task 496\~Task 499 각각이 Task 483을 향하는 `CHILD_OF` 관계를 가지며, ...

1. Task 496: ...
2. Task 497: ...
3. Task 498: ...
4. Task 499: ...
```

**답변 본문(1. 2. 3. 4. 열거)은 요구된 순서를 정확히 지켰다.** `missing` 도 비어 있어 네 번호가 모두
답변에 있다. 문제는 그 앞의 요약 문장 "Task 496\~Task 499" 라는 범위 표기다.

| sourceRefId | needle | 첫 등장 index |
| --- | --- | ---: |
| task-496 | 496 | 9 |
| task-499 | 499 | 18 |
| task-498 | 498 | 345 |
| task-497 | 497 | 379 |

요약 문장의 "496\~499" 표기 때문에 496(index 9)과 499(index 18)가 본문의 1.2.3.4. 열거보다 먼저
등장해, 순서 검사가 실제 등장 순서를 `496 → 499 → 498 → 497` 로 읽는다.

**두 회차의 구체 원인은 다르고 부류는 같다.** 각 회차 첫 attempt 의 첫 등장 위치다.

| 회차 | 496 | 497 | 498 | 499 | 어긋난 지점 |
| --- | ---: | ---: | ---: | ---: | --- |
| 1회차 | 167 | 344 | **314** | 540 | 498 이 497 보다 먼저다 |
| 2회차 | 9 | 379 | 345 | **18** | 499 가 497·498 보다 먼저다 |

1회차 답변 서두에는 번호가 없다 ("네 업무 모두 Task #483을 직접 `CHILD_OF`로 가리키며").
496 은 본문 열거에서 처음 나오지만, **그 496 문단 안에서 498 을 교차 언급**해
("이후 Task #498의 전수 등가성 검증으로 마무리합니다") 498 이 497 문단보다 앞선다.

2회차는 서두 요약 문장이 범위 표기를 써서 496·499 를 먼저 노출한다.

두 경우 모두 **본문 열거 순서는 요구대로이고, 어긋난 것은 문자열 첫 등장 순서뿐이다.**
검사가 "본문에서 각 업무를 설명하는 순서" 대신 "번호가 처음 나오는 위치" 를 보기 때문에 생긴다.

**전송 전환이 만든 회귀가 아니다.** 프롬프트를 한 글자도 바꾸지 않았고 그래프도 건드리지 않았다 —
달라진 것은 LLM 이 고른 답변 문체(요약 문장에 범위 표기를 쓰는지)이고 그건 실행 간 변동 범위다.
