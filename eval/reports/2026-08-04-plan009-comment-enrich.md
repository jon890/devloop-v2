# Plan009 집계 오판정 제거와 댓글 보강 측정 리포트

plan008 이 남긴 두 문제를 고친 변경의 효과를 측정한다.

1. `collect` 를 집계 판정에서 뺐다 — plan008 이 `collect` 를 쓰게 만든 뒤 일반 질의가 집계로 오판정됐다
2. 근거에 온 업무의 댓글을 그래프 조회로 끌어온다 — 오판정 경로가 우연히 하던 근거 보강을 대체한다

## 실행 조건

- 평가 세트: `eval/suites/tc-ocr-api-gateway.json` — **한 글자도 건드리지 않았다**
- 질의 모델: `gpt-5.6-terra` (`.env` 선언값. API 응답이 런타임 모델 id 를 증명하지는 않는다)
- 그래프: 노드 3,082 · 관계 13,002 · Concept 968 (이번 작업은 API 만 고쳤다)
- **실제 측정한 문항 수: 12/12**, 두 측정 모두 36/36 attempts, 오류 0건
- 원시 실행 결과는 `eval/runs/` 에 있고 gitignore 대상이라 커밋하지 않는다

## 중간 단계가 트레이드오프를 드러냈다

`collect` 오판정만 고쳤을 때(집계 판정 수정) **지연은 24초 줄었는데 회수가 2에서 6으로 나빠졌다.**

오판정 경로는 근거를 별도 Cypher 로 다시 모은다. 즉 **잘못된 분기가 우연히 근거 보강 역할을
하고 있었다.** LLM 호출 한 번의 대가로 회수를 얻고 있던 셈이다.

남은 실패 6건을 열어 보니 전부 같은 형태였다.

| 문항 | 못 찾는 근거 | 부모 업무 |
| --- | --- | --- |
| AGW-H03 | `comment-483-lb-blocked` 3회, `comment-483-trust-fixed` 1회 | 483 — 근거에 있다 |
| AGW-H04 | `comment-497-model-buffer` 2회 | 497 — 근거에 있다 |
| AGW-A02 | `comment-497-api-size`·`ingress-size` 각 1회 | 497 — 근거에 있다 |

**업무는 왔는데 그 댓글만 빠진다.** 그러면 LLM 을 다시 부를 필요가 없다. `buildQueryEvidence` 가
근거에 온 Task 의 댓글을 그래프 조회로 끌어오게 했고, 업무당 상한 8을 뒀다 (Task 127 은 댓글이 20건이다).

결과는 **회수는 오판정 경로의 이득을 가져오고 지연 비용은 안 내는 것**이다.

## 의미 판정 범위

두 판정자 의미 판정을 **하지 않았다.** 목표 지표가 결정적 축이고, plan006 에서 36회 중 22회가
채점자 불일치로 `REVIEW` 였던 실측이 있어 정보량이 낮다.

따라서 이 리포트는 **결정적 축만** 근거로 삼는다. 답변 품질의 변화는 판정하지 않았다.

## 얻은 방법론

- **총수가 안 움직이면 실패를 분해한다.** plan007 1차와 plan009 중간 단계에서 두 번 통했다
- **같은 코드로 두 번 재야 구간이 생긴다.** 네 반복 모두 지켰다
- **좋아진 지표의 원인이 의도한 기제인지 확인한다.** plan008 의 개선분 일부가 집계 오판정이라는
  **의도하지 않은 경로**에서 왔다는 것을 이번에 발견했다. 확인하지 않았으면 잘못된 이해가 굳었다
- **부작용은 지표 하나만 보면 안 보인다.** plan008 은 회수만 보면 성공이었다. 지연을 함께 봐서
  오판정을 찾았다
